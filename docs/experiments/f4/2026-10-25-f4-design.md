## 1 为什么有 f4

f3 到 k30 的结果（A3、A0 读者记录）：

- **准确率三组打平**：A3 0.926、A0 0.924、P 0.922。A3 与 A0 的差在 k30 为 $-0.002$，置信区间 $[-0.035, 0.030]$，区间很窄，不是统计功效不足。
- **写入一侧 A3 更省**：到 k30，A0 写者用时 16.1 小时、模型调用 3,407 次、缓存读 3.65 亿；A3 分别为 10.5 小时、1,880 次、1.65 亿。A0 多花的主要是查找：更新类会话用时中位 29.8 分钟对 11.7 分钟，写者在 grep 文件。
- **读取一侧 A0 更省**：340 次读者会话合计，A0 比 A3 用时少 26%，未缓存输入少 33%，缓存读少 21%，输出少 11%；但模型调用多 9%，工具调用多 14%。也就是说，文件读取每步更小、步数更多，总量更省。

两边各省一头。f4 把写入路径固定为 A3（中间件），只换读取路径，要回答：

> 写入经中间件、读取改用文件形态时，能否在准确率不降低的前提下，把读取成本降到 A0 的水平，从而使建库加读库的总成本同时低于 A0 和 A3？读取成本的差别从哪里来？

f4 不改写者、不重新建库：所有组都读 f3-A3 已有的三个检查点（k10、k20、k30）。

## 2 设计空间

写入路径与读取路径各两种取法：

| | 读取：文件形态 | 读取：现有 MCP 工具 |
| --- | --- | --- |
| **写入：约定（files + Git）** | A0（f3） | —— |
| **写入：中间件** | **A3F**（物化）、**A3V**（虚拟） | A3（f3） |

文件形态的读取有两种实现，对应数据库中视图的两种做法：

| | A3F：物化视图 | A3V：虚拟视图 |
| --- | --- | --- |
| 什么时候生成 | 库提交后写成文件树（Git 仓库） | 读取时按需生成 |
| 读者用什么 | pi 自带的 ls、grep、read、bash，能用管道组合 | MCP 上的文件式工具，如 `list(kind)`、`read(id)`、`grep(pattern)` |
| 派生字段（`_stale` 等） | 生成时写进文件 | 读取时现算，与现有 `get` 相同 |
| 是否需要 shell | 需要 | 不需要 |
| 保留的开销 | 视图的刷新 | MCP 往返、工具描述占的上下文 |
| 改不改系统 | 不改（导出在评测侧） | 改：新增 MCP 读取工具 |

两者共用同一个渲染：节点渲染成什么样的 YAML，A3V 的 `read(id)` 就返回什么。

**方法上的原则**〔已确认 2026-10-25，供叙事使用〕：写入需要的保证，agent 靠约定难以在规模增长时稳定做到，由中间件强制；读取需要的访问方式，agent 本来就会，由库把自己呈现成那种形态。系统内的派生数据也按同一边界分两类：文件树是确定的派生，由系统重算；产物是需要判断的派生，系统只标出过时（`_stale`），由写者重写。

## 3 F4-0：从现有轨迹拆解读取成本（不新跑）

〔已确认 2026-10-25〕与 A3F 的接入并行，不挡 A3F（10-25 调整）。它用于解释读取成本；A3V 暂缓后，不再承担决定是否实现 A3V 的作用。若成本主要来自 E-b，审稿人可能认为只是我们的 MCP 工具输出过长，这一点须在论文中先行说明。

f3 读者的成本差别有四种可能的来源，前两种只涉及我们自己工具的设计：

| 解释 | 内容 | 在轨迹中的表现 | 若成立，对 f4 的含义 |
| --- | --- | --- | --- |
| E-a 粒度 | MCP 要走 search → get → read_evidence 多轮；grep 一次返回多处命中 | A3 每题在定位阶段的往返轮数多 | 文件式工具（A3V）可以拿回大部分收益 |
| E-b 输出冗长 | search、get、traverse 的返回过长（早先已记 search 输出过大） | A3 单次工具返回字节数大，未缓存输入与缓存读高 | 同上；也可能只需精简现有工具 |
| E-c 工具描述 | MCP 工具描述每轮都占上下文 | 每轮固定的输入开销 | 工具越少越省 |
| E-d 原生工具 | 读者用自带工具，不需学新接口，能用管道，一次读整份文件 | A0 的成本省在少量大块读取与管道组合上 | 只有真正的文件（A3F）能拿到 |

f3 已有的线索：A0 的模型调用与工具调用比 A3 多，token 与用时却更少（第 1 节），倾向 E-b 或 E-c，但还没有拆开。

拆解口径〔已确认 2026-10-25〕：A3、A0 与 P 三组读者，k10、k20、k30 的主题集（53、69、200 题，不含辅助题），逐题配对统计——

- **按工具的调用次数与返回大小**：A3 按工具名（search、get、traverse、checkout、read_evidence 等）；A0、P 的 bash 按管道中的命令归类（grep、rg 为搜索；cat、head、sed、tail 为读取；ls、find 为列目录；python、awk 为脚本；git；其他），另计 pi 的 read 与 read_evidence。大小记字符数。
- **定位成本**：每题第一次调用 `read_evidence` 之前的模型调用次数；从未调用的会话另计，不记为 0。
- **固定开销**：每个会话第一次模型调用的提示 token（input 加 cacheRead），扣去题面。两组来源不同：A0 的系统提示含 pi 载入的 `AGENTS.md`（`project_context`，约 7.9k 字符），A3 没有这一段，但多了 MCP 工具的定义。所以 E-c 比的是 A0 的说明文字对 A3 的工具说明。
- **驻留成本**（区分 E-b）：一次工具返回或助手输出进入上下文后，之后每次模型调用都会再读一遍，直到压缩。按来源汇总，把每组提示 token 的总和拆为固定前缀、各工具的返回、助手输出与残差：
  - 助手输出取 usage 的精确值。读者会话只有一条用户消息，按模型的 chat template，思考内容也留在上下文中。
  - 工具返回的 token 按字符数除以每组校准的比例估计。
  - 残差逐题报告。
- **按题型报告**：k30 主题集实际是 T1–T11 与 T14。跨论文题（T3、T7、T8）与单篇查找题（T9、T10、T11、T14）另外合并报告。

实现：抽取为 `pweval.measure.read_cost`，读各组的回答记录与事件流，表写到 `~/pw-lab/runs/f3/analysis/f4-0/`，附来源与核对；切片与作图在 `eval/notebooks/f4_0_read_cost.ipynb`，只读这些表（AGENTS.md 中 notebook 的规则）。

文献依据：SWE-agent（`2024-SWE-agent`）的 agent-computer interface 表明为 LM 设计的接口优于直接给 shell，并给出四条原则（动作简单、动作紧凑、反馈充分而简洁、护栏）；它还发现逐条翻看的搜索会耗尽预算。它支持“把读取工具做成 agent 好用的形状”，不能用来支持“agent 天生偏爱 grep”。

### 4.2 与 A3、A0 的差别

**A3F 对 A3**：库的内容相同，派生字段出自同一份代码，只换读取方式。这是读取路径的干净比较。仍有的差别：

- 派生字段只在最后一个提交里，历史提交不带（说明文字已写明）；
- A3F 每个文件都直接带着派生字段，A3 要调用 `get` 才看到；
- A3F 没有向量检索，只有文本搜索。

**A3F 对 A0**：两套系统的整体比较。库的内容不同（各自写者建的库），说明文字不同（A3F 没有模板，多了只读字段一节），论文中须写明。

## 5 A3V：虚拟视图

〔暂缓 2026-10-25〕先验证 A3F；A3F 若成功，已足以支撑主要结论。暂缓的理由（用户）：MCP 工具是写者与读者共用的，写者在写入前同样要查找。若文件式工具只给读者并且降低了成本，自然要问建库时是否也该提供它们；而一旦提供给写者，写入条件就变了，须重新建库，与 A3 的已有结果不再可比。A3F 不改 MCP 工具集，没有这个问题。

以下保留为设计空间中的一个点，不实现。设想是在 MCP 上提供文件式的读取工具，读者像在文件目录中一样工作：

- `list(kind)`：列出某类节点或产物的 id 与标题，相当于 `ls store/nodes/<kind>`；
- `read(id)`：返回该节点或产物渲染后的全文，与 A3F 的文件逐字相同（含读取时现算的 `_` 字段）；
- `grep(pattern, kind?)`：在渲染后的文本上搜索，返回命中的 id、行与少量上下文，结果有上限并给出总数（SWE-agent 的汇总式搜索）；
- `log`、`show` 保留，用于历史。

若日后重启，须先决定：

1. 只给文件式工具，还是与现有的 search、get、traverse 并列。只给文件式工具，比较最干净；并列更接近最终系统的形态。
2. 这是系统改动（新增 MCP 工具），须先过设计评审并写进 `docs/designs/v3/tools.md`；A3 读者的冻结副本不变，A3V 用新的冻结副本。
3. 若 F4-0 显示成本主要来自 E-b（输出冗长），另一个更便宜的选项是只精简现有工具的输出。它改动的是 A3 本身，要与 A3 的已有结果分开报告。

## 9 结论的边界

- **事后设计**：A3F 是看了 f3 的结果之后提出的，论文中如实写（“A0 显示文件读取便宜，于是把它纳入设计”）。题库在 f3 中已用过；以后若有新论文或新题目复测，可信度更高。
- **只有读者用视图**：A3F 只给读者。按 AGENTS.md 的两条访问路径，写者在写入前的查找也可以读这份视图；这能否进一步降低写入成本（f3 中 A3 写者已比 A0 省），f4 不回答。
- **单一 agent 与模型**：只用 pi 与一个 27B 模型。“任何 agent 都能用文件视图”是论证，不是本实验的结论。
- **视图在检查点上离线生成**，派生字段只在最后一个提交里；实验不检验“每次提交后刷新”。
- **不是物化视图技术的贡献**：没有增量维护、借助视图改写查询或多视图选择。可以说的是：库是唯一的权威记录，文件树是它的只读物化视图，带派生状态，状态与库的提交一一对应。
- **过时标记偏粗**：k30 有 10/15 的产物带 `_stale`，主要原因是 `superseded` 及其传递的 `stale input`；被引用的产物出新版本时，下游一律报 `superseded`（`tools.md` 已记）。这对 A3 与 A3F 相同，不影响二者的比较，但关系到“过时标记有用”的说法，须在库层审计中抽查准确率。
- **不替代库层审计**：f3 的准确率打平之后，“库更健康”的主张只能靠审计支撑。f4 回答的是读取成本，与审计并行推进。
- 规模只有 30 篇论文；文件读取的优势在更大规模下是否保持，不由本实验回答。
