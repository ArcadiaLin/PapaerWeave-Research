# f3：局部材料访问下的各组条件（设计）

状态：讨论稿（2026-10-22）。已确认：材料 ID、来源服务的形式、A3/A2 两个读原文入口并存、写者侧其他部分冻结（第 4、8 节）；其余待定。标记沿用 V3：〔已确认 日期〕为用户已确认；〔提议〕为本文提出、尚未确认；〔待定〕为尚未决定的细节。
来源：`tmps/2026-10-22-A3-rewrite.md`（写者信息条件的整合方案），10-22 关于 f2-A3 定位与协调组的讨论。
依据：`docs/designs/v3/evaluation.md`（V3 评测），本文改动它的地方逐条标出；f2-A3 的定位见 `docs/experiments/f2/2026-10-21-f2-A3-writers.md`。

## 1 为什么有 f3

f1、f2 的写者从第一个会话起就能看到全部 30 篇论文与代码，可以绕过库直接读、grep 尚未入库或别人建过的论文，库不是写者之间唯一的通道。主流的记忆评测（LongMemEval、MemoryAgentBench）都按时间顺序把材料逐步交给被测系统；我们的设定更依赖这一点，因为要检验的正是后来者能否经库发现、核查并接续前人的贡献。

f3 只改写者的信息条件：**每个写者带着当前任务进入自己的工作空间，用本次任务提供的材料与共享库中的历史贡献完成工作，再把结果提交回共享库。** 不预先提供全套论文，不禁止核查已开放的原文，不限制 agent 使用正常的文件与 shell 工具。

f3 要检验的是：

> 局部任务持续带来新材料时，不同的存储方案能否让后来的写者发现、核查并接续此前的贡献，以及为此付出多少成本。

不研究协调协议：不引入协调者或跨写者的消息通道（10-22 讨论）。f2-A3 保留为全材料访问参照，不是协调组。

## 2 写者能访问什么

〔提议〕每个会话有三个入口，四组相同：

| 入口 | 内容 |
| --- | --- |
| 当前任务 | 任务文字，以及本次直接提供的材料 ID |
| 私人工作空间 | 该写者身份自己的草稿、脚本、已读取的材料与会话文件；同一身份跨会话保留，其他身份不可见 |
| 本组的共享库 | 此前各写者的贡献：记录、产物及其来源引用 |

- 沙箱不挂载论文目录与代码目录，断网（V3 §7 第 5 条照旧）。
- 共享库是写者之间发布与获取贡献的唯一通道；私人工作空间不是公共成果库。
- 现状：A3、A2、A4 的私人工作目录本来就按身份保留（`<组>/writers/<身份>/work`）；变化只在不再挂载 `papers/` 与 `code/`。A0 不同：它的 `/work` 是共享仓库的工作树，所有写者共用一份，会话之间不清理（f1 跑完时仓库里留着未提交的改动），A0 写者没有私人目录。

**读到的原文存在哪里**（10-22 讨论）：

1. 〔已确认 2026-10-22〕`read_source` 不自动存文件，只把内容返回到 agent 的上下文；要不要存、存在哪里由 agent 决定。pi 截断时存下的全文在 `/tmp`，每个会话独立，会话结束即消失。
2. 〔已确认 2026-10-22〕私人工作目录照旧按身份跨会话保留，其他身份看不到。
3. 〔待定，倾向调整；用户与 codex 另议〕**A0 与其他组同一条规则：私人存的只有自己能看到，写者之间只经共享库传递。** 现状下 A0 写者把读到的全文随手存成文件、不提交，后来的 A0 写者都能 grep 到，A0 不付发布的代价就攒出一份共享原文。提议：A0 写者也有按身份保留的私人目录（如 `/work/scratch`，在仓库中忽略）；共享仓库在每个会话开始时回到最后一次提交，上一位写者未提交的改动不留给下一位，运行器记下被丢弃的内容，作为“写了未发布”的知识流失（V3 §4）。这要改 A0 的约定文档；按文字对等，A3 一侧也要说明私人目录。
4. 〔待定，用户另议〕**原文怎样进入共享库。** 提议：都由写者自己动手，运行器不自动放。A3、A2 建库时登记 Paper 的材料，全文即可经 `read_evidence` 被所有人读到；A0 写者把论文文件提交进仓库，效果相同。

## 3 材料怎样随任务提供

### 3.1 每类会话直接提供的材料

〔提议〕清单由任务文字预先确定，不依据读者题目或答案选择：

| 会话（数量） | 直接提供 |
| --- | --- |
| build（28）、build-overlap（7） | 指定的那一篇论文 |
| compare（4） | 指定的两篇论文 |
| update（3） | 指定论文的新旧两个版本 |
| verify-own（3） | 该论文；不额外提供代码 |
| verify-later（3） | 被核查的论文；后来的相关论文从共享库发现 |
| note-i6（2） | 该论文及其固定 commit 的官方代码仓库 |
| note-i1（2） | 不直接提供，从共享库选型 |
| leaderboard（14）、summarize（4） | 不直接提供，从共享库发现输入 |

“提供”是在任务中给出可读的材料 ID，不把文件挂进沙箱。

### 3.2 开放、历史与未开放

〔提议〕

| 状态 | 写者怎样知道 | 能否读 |
| --- | --- | --- |
| 本次任务直接提供 | 任务给出 ID | 全文 |
| 此前已开放 | 从共享记录、产物引用或自己的私人历史中得知 ID | 全文 |
| 尚未开放（含未来版本） | 不提供 | 不能读，即使猜中 ID |

- 开放时间由计划表决定，四组一致：种子材料在起点开放，其余材料在第一次直接提供它的会话开始时开放，此后一直可读。
- 开放与某组是否写进了库无关。“已开放”是来源服务允许读取；“已贡献进库”是写者实际留下了别人能发现的记录、引用或产物。来源服务不替写者把材料 ID、摘要或记录发布进库。
- 推论：只有 2 个代码仓库（Autoformer、CATS，随 note-i6）会开放；f2 中写者能看到 27 个仓库。

## 4 来源服务 `read_source`

〔已确认 2026-10-22〕**一个独立的 MCP 服务，模拟从 arXiv、代码托管站等外部来源取材料**：它不属于任何一组的库，四组相同，只是按计划表决定材料何时“发表”。与真实的 arXiv 不同，它不能检索、不能列目录，这是有意的限制：发现材料必须经库完成，否则写者可以在“arXiv”上直接搜，绕过库。论文中说明这一点。

〔提议〕接口：

```text
read_source(material_id, start_line?, end_line?)      # 论文
read_source(material_id, path?, start_line?, end_line?)  # 代码仓库：列出仓库内文件，或读某个文件
```

- 返回固定版本的内容、材料 ID 与稳定行号；各组同一分页、返回格式与单次上限。
- 可以按 ID 读已开放材料的全文，不要求所读行已被锚点覆盖（这是写者的入口；读者另有规则，见第 6 节）。
- 不提供全部材料的列表、跨论文全文检索或相关推荐；不抽取、不总结、不判断。
- 代码仓库可以列出仓库内的文件，但不能借此枚举别的仓库。
- 拒绝（未开放、不存在、格式错误）逐次记录。
- agent 读到的内容可以存进私人工作空间，用 `read`、`grep` 与脚本处理；也可以把读到的片段写进共享库。这些都是它实际付出的读写成本，不是框架免费给的全语料目录。

细节：

1. 〔已确认 2026-10-22〕**材料 ID：** 论文用带版本的 arXiv 编号（如 `2205.13504v2`），代码用 `<仓库>@<commit>`：稳定、不编码答案或开放顺序、不暴露宿主机路径。题库与 A0 的约定已经在用这种写法。
2. 〔已确认 2026-10-22〕**形式：** 独立的 MCP 服务，四组都接（A0 原本不接 MCP，只加这一个只读工具，不改变“文件 + Git”的本质）；工具说明四组逐字相同。
3. 〔待定〕**单次返回的上限。** pi 把超过 20 KiB 的 MCP 返回从中间截掉，全文存到 `/tmp`（f2-A3 的 `read_evidence` 有 18/182 次被截，只有 5 次回读了全文）。`read_source` 的单次上限应低于这个值，并在返回中给出下一页的行号。
4. 〔已确认 2026-10-22〕**A3、A2 两个入口并存。** `read_source` 四组相同；`read_evidence` 是被测系统的一部分，照旧保留。`read_evidence` 按行号读库中已登记的材料：`<论文节点或材料 id>::<起>:<止>` 找到登记的材料（材料根目录中按内容哈希核对过的文件），返回那几行，附章节名，可用 `at` 读旧版本，也能读产物文档。它只能读有人登记进库的材料（有人建过的论文与产物文档）；运行器只在材料开放时把它放进材料根目录，所以它能读的都已开放，信息上不多于 `read_source`。写者不限锚点，读者为 `anchored`（第 6 节）。
5. 〔提议〕**建库时登记材料的写法。** A3、A2 的写者在 Paper 上写 `material: papers/<id>/paper.md`（相对于材料根目录）。工具说明的示例写着“the Markdown you read”，f2 中这正是写者在 `/work/papers` 里看到的文件；f3 中写者手里没有这个文件，只能照约定写路径。只改这句说明，例如“papers/<arXiv id with version>/paper.md, the paper you read with read_source”，系统代码不动；算作材料条件的一部分。

## 5 各组的写者条件

〔提议〕

| 组 | 共享贡献的存储与发现 | 核查原文 |
| --- | --- | --- |
| A3 | 完整 PaperWeave（MCP）：身份、修订约束、过时标记、受影响产物 | `read_source`（及 `read_evidence`，见第 4 节第 4 条） |
| A2 | 同一服务，关掉查重、修订约束、过时标记、受影响产物四项 | 同上 |
| A0 | 共享 git 仓库：直接搜索、读取、编辑共享记录与产物，经 Git 发布 | `read_source` |
| A4 | Graphiti 的 episode 写入与检索 | `read_source`；写者可在 episode 中记下材料 ID 与行号 |

- A0 可以 grep 共享仓库中的知识文件，但框架不把历史原文放进它的仓库。
- A4 通过来源服务保留核查原文的能力；论文中标明它用了统一的来源服务。
- 各组写者都被要求保留可追溯的来源引用；漏写、写错、后来找不到，都是实际表现的一部分，框架不事后补齐。
- 产物进入私人工作空间：A3、A2 用已有的 `checkout` 取出当前版本、本地编辑、`commit` 发布；A0 直接编辑仓库文件、经 Git 发布；A4 按 episode 记录，不模拟 PaperWeave 的产物类型与版本接口。

**分析时的区分**（以排行榜维护为例：任务不给论文 ID，写者要从库中发现新贡献）：

- 应写入却未写入：写入遗漏；
- 记录存在却没找到：发现失败；
- 找到证据却处理错误：理解或维护失败。

## 6 读者与参照组

- **写者组的读者：** 读者协议独立于本文。A3、A2 的读者照 V3 §2.2 只读库、按记录过的锚点读原文（`anchored`，已实现）。〔待定〕A0、A4 的读者用同样规则：有了统一的来源服务后，可以从各组检查点的库中机械地收集锚点，作为来源服务对读者的放行名单。
- **C、D、P：** 不因 f3 重跑。P 在每个检查点拿到的是计划表中已入库的论文，与 f3 的开放规则一致；ref1 的结果仍然有效。
- **f2-A3：** 全材料访问参照，读者按同一协议在它的 k10、k20、k30 备份上作答，按描述性参照报告。

## 7 要改的材料与代码

- **任务文字（题库 `tasks/plan.yml`）：** 38 个 build、build-overlap、update 任务写着 `papers/<id>/paper.md`，2 个 note-i6 任务写着 `code/` 与 `code/README.md`，都要改成材料 ID 与 `read_source` 的说法；compare、verify 任务是否点出 ID〔待定〕。题库是冻结材料，改动要经确认，在新的冻结记录中标出。
- **工具说明：** `read_source` 的说明，四组逐字相同；`{TOOLS}` 的逐组提示可能要加一句。
- **运行器（`eval/src/pweval/harness/timeline.py`）：** 不再复制、挂载论文与代码目录；按计划表维护开放状态；每个会话把材料清单写进 `sessions.jsonl`。A3、A2 的材料根目录（MCP 服务登记材料用）照旧在沙箱外。
- **记录：** 每个会话的材料清单、材料的开放时刻与版本；`read_source` 的每次读取（ID、范围、返回量）与拒绝。其余照 f2：会话轨迹、工作目录快照、库版本、检查点备份。

## 8 运行

- 〔提议〕A3 先跑，A2、A0、A4 随后；服务的分配与并发照 V3 §7 第 1 条。不在旧库上中途切换条件：f3 各组都从种子重新建库。
- 〔已确认 2026-10-22〕写者侧除材料条件与来源服务（含第 4 节第 5 条的说明改动）之外全部冻结；pi 的 20 KiB 截断、上下文溢出后的压缩等已知问题不修，以保持与 f2-A3 的对照。

## 9 结论的边界

- 关注贡献是否保留、产物是否被复用并正确更新、变化是否被发现，以及维护与后续使用的成本；不以 `checkout` 或 `read_source` 调用多为成功。
- 本设计只调整写者的信息条件，不检验协调协议，也不声称与协调系统等效。
- 写者数与写入量仍然同时增长，H2 只能说明“随积累，库能否保持”（V3 §3、§9）。
