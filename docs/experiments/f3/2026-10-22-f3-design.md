# f3：局部材料访问下的各组条件（设计）

状态：讨论稿（2026-10-22）。已确认：每会话全新工作目录、来源下载到本次目录、只继承共享库已发布内容（第 2 节）；统一来源 ID 与可选定位的 anchor、各组写者统一使用 read_source、各组读者统一使用只读锚点所在块的 `read_evidence`、Content 等 grounded 记录必须带定位（第 4、6 节）；冻结范围见第 8 节。上述设计变更尚未实现；其余待定。标记沿用 V3：〔已确认 日期〕为用户已确认；〔提议〕为本文提出、尚未确认；〔待定〕为尚未决定的细节。
来源：`tmps/2026-10-22-A3-rewrite.md`（写者信息条件的整合方案），10-22 关于 f2-A3 定位与协调组的讨论。
依据：`docs/designs/v3/evaluation.md`（V3 评测），本文改动它的地方逐条标出；f2-A3 的定位见 `docs/experiments/f2/2026-10-21-f2-A3-writers.md`。

## 1 为什么有 f3

f1、f2 的写者从第一个会话起就能看到全部 30 篇论文与代码，可以绕过库直接读、grep 尚未入库或别人建过的论文，库不是写者之间唯一的通道。主流的记忆评测（LongMemEval、MemoryAgentBench）都按时间顺序把材料逐步交给被测系统；我们的设定更依赖这一点，因为要检验的正是后来者能否经库发现、核查并接续前人的贡献。

f3 调整写者的信息条件，并统一证据引用与读者来源访问协议：**每个写者带着当前任务进入自己的工作空间，用本次任务提供的材料与共享库中的历史贡献完成工作，再把结果提交回共享库。** 不预先提供全套论文，不禁止核查已开放的原文，不限制 agent 使用正常的文件与 shell 工具。

f3 要检验的是：

> 局部任务持续带来新材料时，不同的存储方案能否让后来的写者发现、核查并接续此前的贡献，以及为此付出多少成本。

不研究协调协议：不引入协调者或跨写者的消息通道（10-22 讨论）。f2-A3 保留为全材料访问参照，不是协调组。

## 2 写者能访问什么

〔提议〕每个会话有三个入口，四组相同：

| 入口 | 内容 |
| --- | --- |
| 当前任务 | 任务文字，以及本次直接提供的材料 ID |
| 私人工作空间 | 本次会话的草稿、脚本、下载材料与会话文件；每次重新开始，同一身份下次也不继承 |
| 本组的共享库 | 此前各写者的贡献：记录、产物及其来源引用 |

- 沙箱不挂载论文目录与代码目录，断网（V3 §7 第 5 条照旧）。
- 共享库是写者之间发布与获取贡献的唯一通道；私人工作空间不是公共成果库。
- 现状：A3、A2、A4 的私人工作目录本来就按身份保留（`<组>/writers/<身份>/work`）；f3 改为每会话全新目录，也不再挂载 `papers/` 与 `code/`。A0 不同：它的 `/work` 是共享仓库的工作树，所有写者共用一份，会话之间不清理（f1 跑完时仓库里留着未提交的改动），A0 写者没有私人目录。

### 2.1 每会话重新开始，只继承共享库

〔已确认 2026-10-22〕四组每个新会话使用全新的本地工作目录，pi 的 cwd 为 `/work/`。即使沿用同一写者身份，也不继承上一会话的私人下载、草稿、脚本或未发布文件；home 中的会话记忆同样不得跨会话继承，运行所需固定配置照常提供。共享库持续保留。

| 会话开始与交接 | A0 | A3 / A2 | A4 |
| --- | --- | --- | --- |
| 开始时的工作空间 | 全新 `/work/`，在 `/work/store/` 取出共享 Git 最新已发布状态 | 全新 `/work/`，连接已有 PaperWeave | 全新 `/work/`，连接已有 Graphiti |
| 获取来源 | `read_source` 下载到本次 `/work/sources/` | 同左 | 同左 |
| 发布贡献 | 选择文件并 Git 提交 | 通过系统接口提交记录与产物 | 写入 episode |
| 下一会话继承 | Git 已发布文件与历史 | 库中已发布记录、来源引用与产物 | 库中已发布 episode |

`read_source` 将指定来源的固定版本下载到本次 `/work/sources/`，返回本地路径、版本、行数与内容哈希；论文保存为 Markdown，代码保留仓库内目录结构。agent 使用 pi 自带的 `read`、`grep` 与 shell 阅读和处理。四组采用相同的下载行为，只有主动请求的已开放材料才落盘，不预装全部语料。

**下载不等于发布，下载原文不自动传给下次会话。** 此规则替代此前“只返回上下文、不自动存文件”与“私人目录按身份跨会话保留”的约定：

- A0 可以主动把全文提交进 Git，之后其他会话就能直接读、grep；这是文件方案的正常能力，不禁止，也不强制。
- A0 也可以只提交笔记及来源 ID、版本和可选的证据定位；后来者据此调用 `read_source` 重新获取原文，不必要求前人先提交全文。
- A3、A2 从库中取得来源引用后，同样调用 `read_source` 获取固定版本原文，不依赖前人的本地文件或以 PW 内部材料 ID 定位论文。需要产物文件时调用 `checkout`。
- 来源服务不自动向任何共享库写入全文、材料 ID、摘要或引用。共享内容由 agent 自己发布，计入实际存储与读写成本。

### 2.2 A0 的 Git 发布与会话归档

〔已确认 2026-10-22〕A0 共享的是已发布的 Git 历史，而不是上一会话的未提交工作树。每个会话在全新工作目录中取出公共仓库的最新已发布状态，不需要按身份维护长期工作副本。

〔提议〕发布操作沿用 Git：agent 自己选择文件并执行 `git add <选定文件>`、`git commit`；框架负责同步新提交，不代选文件、不自动执行 `git add -A && git commit`。约定文档明确说明：**本次需要共享的记录与产物写入 `/work/store/`，选择对应文件并提交；私人下载与草稿留在 `/work/` 的其他目录。** 要求发布的是本次贡献，不是整个工作空间，也不要求提交读过的全文。其他组同样说明本地工作与调用各组接口发布的区别。

〔已确认 2026-10-22〕会话结束时，未发布内容保存在评测快照或归档中供审计，不自动挂给后续会话，也不向原身份提供跨会话恢复入口。归档不属于 agent 可查询的共享库。未提交内容计为**未发布贡献**；已发布且正确的内容后来消失，才计为已积累知识的流失，不能把会话目录清理记成存储方案的知识流失。

新会话与基础设施中断后的同一会话重试必须区分。〔待定〕中断重试是否恢复该次现场及如何记录，单独固定；不得默默沿用旧的按身份目录续跑行为，或把恢复机制变成后续任务的私人记忆通道。

## 3 材料怎样随任务提供

### 3.1 每类会话直接提供的材料

〔提议〕清单由任务文字预先确定，不依据读者题目或答案选择：

| 会话（数量） | 直接提供 |
| --- | --- |
| build（28）、build-overlap（7） | 指定的那一篇论文 |
| compare（4） | 指定的两篇论文 |
| update（3） | 指定论文的新旧两个版本 |
| verify-own（3） | 该论文；不额外提供代码 |
| verify-later（3） | 被核查的论文；后来的相关论文从共享库发现 |
| note-i6（2） | 该论文及其固定 commit 的官方代码仓库 |
| note-i1（2） | 不直接提供，从共享库选型 |
| leaderboard（14）、summarize（4） | 不直接提供，从共享库发现输入 |

“提供”是在任务中给出可读的材料 ID，不预先挂载材料；agent 调用 `read_source` 后，指定材料才下载到私人目录。

### 3.2 开放、历史与未开放

〔提议〕

| 状态 | 写者怎样知道 | 能否读 |
| --- | --- | --- |
| 本次任务直接提供 | 任务给出 ID | 全文 |
| 此前已开放 | 从共享记录、产物引用或本次会话已经获取的材料中得知 ID | 全文 |
| 尚未开放（含未来版本） | 不提供 | 不能读，即使猜中 ID |

- 开放时间由计划表决定，四组一致：种子材料在起点开放，其余材料在第一次直接提供它的会话开始时开放，此后一直可读。
- 开放与某组是否写进了库无关。“已开放”是来源服务允许读取；“已贡献进库”是写者实际留下了别人能发现的记录、引用或产物。来源服务不替写者把材料 ID、摘要或记录发布进库。
- 推论：只有 2 个代码仓库（Autoformer、CATS，随 note-i6）会开放；f2 中写者能看到 27 个仓库。

## 4 来源服务 `read_source`

〔已确认 2026-10-22〕**一个独立的 MCP 服务，模拟从 arXiv、代码托管站等外部来源取材料**：它不属于任何一组的库，四组相同，只是按计划表决定材料何时“发表”。与真实的 arXiv 不同，它不能检索、不能列目录，这是有意的限制：发现材料必须经库完成，否则写者可以在“arXiv”上直接搜，绕过库。论文中说明这一点。

〔提议〕接口：

```text
read_source(source_id)  # 下载固定版本来源到本次会话的私人来源目录
```

- 返回材料 ID、固定版本、本地路径、内容哈希及论文行数；代码返回本地根目录与清单文件路径，清单记录文件路径、行数和哈希。全文不塞入 MCP 返回，由 agent 用文件工具按需读取；各组同一下载与返回格式。
- 可以按 ID 读已开放材料的全文，不要求所读行已被锚点覆盖。这是四组写者的入口；读者不用它，另有只读锚点所在块的工具（第 6 节）。
- 不提供全部材料的列表、跨论文全文检索或相关推荐；不抽取、不总结、不判断。
- 下载后的代码仓库可以列出仓库内的文件，但不能借此枚举别的仓库。
- 拒绝（未开放、不存在、格式错误）逐次记录。
- 下载只写入当前身份的私人来源目录，不写入 `/work/store/` 或其他共享库。同一材料的本地副本若已被改动，不能静默覆盖；保留已有文件并另存可核验的来源副本。重复下载与路径规则在实现前固定，四组一致。
- 记录来源请求、下载字节数及本地副本复用情况；后续文件读取由会话轨迹审计。下载字节数不等于模型实际读到的内容量，也不等于输入 token 成本。

细节：

1. 〔已确认 2026-10-22〕**外部来源 ID（source_id）：** 论文用带版本的 arXiv 编号（如 `2205.13504v2`），代码用 `<仓库>@<commit>`：稳定、不编码答案或开放顺序、不暴露宿主机路径。题库与 A0 的约定已经在用这种写法。
2. 〔已确认 2026-10-22〕**形式：** 独立的 MCP 服务，四组都接（A0 原本不接 MCP，只加这一个只读工具，不改变“文件 + Git”的本质）；工具说明四组逐字相同。
3. 〔提议〕**返回大小与文件交付。** MCP 只返回简短的下载结果，控制在 pi 的 20 KiB 截断阈值以内；大代码清单放在本地文件中，不分页返回全文。pi 自带文件工具的截断与上下文行为保持不变。来源服务只可将请求的材料交付到当前会话对应身份的私人目录；不得借文件交付访问其他身份目录或枚举未请求材料。
4. 〔已确认 2026-10-22〕**统一读取来源。** 各组写者都通过 `read_source(source_id)` 获取来源，再用普通文件工具阅读或搜索；读者的入口见第 6 节。写者不再依赖 PaperWeave 的 `read_evidence`，也不再采用基于 PW 内部论文／Material ID 的证据引用。这替代此前“两入口并存”的约定；当前实现仍使用旧机制，需要修改，不能只改提示词。
5. **来源持久性。** 固定版本原文由来源服务持久持有，本次工作目录只是下载副本。相同 `source_id` 必须对应相同内容及规范化格式，并可用哈希核验；不能每次重新转换出不同行号的论文文本。证据解析不依赖上一会话的文件，也不要求 PaperWeave 另存一份论文副本。系统提交校验如何接入来源解析能力属于待实现细节。

### 4.1 anchor：来源 ID 与可选定位

〔已确认 2026-10-22〕**anchor 是可解析的来源引用，不限定为行号范围。** 语义形式为：

```text
<source_id>[::<locator>]
```

- `source_id` 必填，与 `read_source` 使用的是同一个外部来源 ID，不是 PW 自动分配的节点 ID，也不是本次下载的本地路径。
- `locator` 可选，标识来源内部的位置：整个文件、文件中的行号范围、章节、页面片段等均可，只要有明确的解析方式。省略时指向整个来源。
- 边与产物中的引用推荐提供行号以便精确定位，但不强制，没有行号不构成无效引用（Content 等 grounded 记录除外，见下条）；位置存在也不代表它支持所述结论，语义正确性仍需另外评测。
- 〔已确认 2026-10-22〕**Content 等 grounded 记录必须带定位。** Content 的 anchor 现在就是必填字段（`system/src/paperweave/model/schema.py` 中 Content 的必填项为 `paper`、`anchor`、`description`），f3 进一步要求其中每条都给出来源内部的定位，提交校验拒绝只写来源的 anchor；修订 grounded 记录仍须带 anchor 与理由。边与产物中的来源引用可以只写来源。
- 〔提议〕没有定位的 anchor 对读者不放行任何段落（第 6 节）：它说明了来源，但没有把读者带到来源中的某处。各组无定位 anchor 的比例作为指标报告。
- 当前 artifact 不作为证据来源，不引入 `pw:` 分支。产物的存储、依赖关系与 `checkout` 不因此取消。

以下是语义示例；分隔符、转义与各来源类型的定位语法须在实现前固定，避免路径和 URL 歧义：

```text
2205.13504v2                         # 整篇论文
2205.13504v2::210:245                 # 论文中的行号范围
repo@<commit>::src/model.py          # 固定版本仓库中的整个文件
repo@<commit>::src/model.py::30:48    # 文件中的行号范围
<网页快照ID>::#experimental-results  # 固定网页中的片段（扩展示例）
```

网页等来源是可扩展方向，不要求 f3 实现网页支持；本轮先覆盖论文与固定版本代码仓库。

写者在 graph-doc 中直接填写来源引用，例如：

```yaml
paper: paper_0001
anchor: ["2205.13504v2::210:245"]
```

`paper` 仍是记录所属论文的库内 ID；`anchor` 独立说明证据的外部来源与可选位置。agent 从任务或 `read_source` 返回中取得准确来源 ID，不猜内部 Material ID，不用私人文件路径代替来源 ID。

提交校验从“当前论文材料中的裸行号”改为“来源可解析；若给出定位，该位置存在”，并保留来源与记录所属论文的对应校验（包括官方代码等允许的关联来源）。代码文件必须定位到对应固定 commit；具体解析与关联校验规则在实现前固定。不能自动补写 agent 未提供的局部证据定位。

写者的读取流程：从共享记录或产物中发现 anchor，取出 `source_id`，调用 `read_source` 获取固定来源，再按 locator 用文件工具定位；没有 locator 时由 agent 自行搜索和阅读。对写者，anchor 用于定位，不是全文访问的权限清单；对读者，库中记录的 anchor 就是可读段落的放行名单（第 6 节）。

## 5 各组的写者条件

〔提议〕

| 组 | 共享贡献的存储与发现 | 核查原文 |
| --- | --- | --- |
| A3 | 完整 PaperWeave（MCP）：身份、修订约束、过时标记、受影响产物 | `read_source` |
| A2 | 同一服务，关掉查重、修订约束、过时标记、受影响产物四项 | 同上 |
| A0 | 共享 git 仓库：直接搜索、读取、编辑共享记录与产物，经 Git 发布 | `read_source` |
| A4 | Graphiti 的 episode 写入与检索 | `read_source`；写者可在 episode 中记下来源 ID 与可选定位 |

- A0 可以 grep 已发布的知识文件及写者主动提交的原文，但框架不把历史原文放进它的仓库。私人下载在仓库外，不会因提交本次笔记而自动进入 Git。A0 写者提交整篇原文不禁止，按次计数报告：之后 A0 读者能 grep 这些全文，而 A3、A2 登记的论文对读者只放行锚点块，这一不对称是文件方案“把原文发布进库”的代价与收益，报告时标出。
- A4 通过来源服务保留核查原文的能力；论文中标明它用了统一的来源服务。
- 各组写者都被要求保留可追溯的来源引用；漏写、写错、后来找不到，都是实际表现的一部分，框架不事后补齐。
- 产物进入私人工作空间：A3、A2 用已有的 `checkout` 取出当前版本、本地编辑、`commit` 发布；A0 直接编辑仓库文件、经 Git 发布；A4 按 episode 记录，不模拟 PaperWeave 的产物类型与版本接口。

**分析时的区分**（以排行榜维护为例：任务不给论文 ID，写者要从库中发现新贡献）：

- 应写入却未写入：写入遗漏；
- 记录存在却没找到：发现失败；
- 找到证据却处理错误：理解或维护失败。

## 6 读者与参照组

〔已确认 2026-10-22〕**读者不用 `read_source`，四组统一使用只读锚点所在块的 `read_evidence`。** 读者能读全文时，几乎每篇已开放论文都有某条记录指向它，读者就成了“P 组加上库”，库的作用缩到“把方法名对上来源 ID”，直接读原文得到的收益混进了组间比较。V3 §2.2 的原则照旧：库把读者带到哪里，读者就读到哪里。

- **工具：** 〔已确认 2026-10-22〕名为 `read_evidence`，四组的工具与说明逐字相同。A0、A4 没有 PaperWeave 服务，所以它由评测侧提供；A3、A2 的读者工具列表中只有这一个 `read_evidence`，不再暴露 PaperWeave 自己的同名工具。〔提议〕输入 `<source_id>::<locator>`，返回定位所在整块的文字（带行号，表格给整张表），直接放在返回中、不落盘；不在放行名单内时拒绝，并列出该来源能读的范围。
- **放行名单：** 该组检查点的共享贡献中记录过的 anchor，扩到所在的块（与 `system/src/paperweave/query/anchored.py` 的 `block`、`readable` 及 D 组取段落的规则相同），四组用同一条匹配规则机械收集：
  - A3、A2：Content 与边的 anchor、产物 `USED` 边的定位、产物文档（含旧版本）正文中的来源引用；
  - A0：检查点提交时仓库文件正文中的来源引用；
  - A4：episode 正文中的来源引用。
- 没有定位的 anchor 不放行段落（第 4.1 节）；未开放材料拒绝；开放状态与放行名单都固定在对应检查点。
- A0 读者照常读、grep 检查点仓库中的文件，这是文件方案本身的能力；读原文只经上述工具。
- 此规则沿用 V3 §2.2 的原则，替代其中只限 A3、A2 的 `anchored read_evidence` 实现：A3、A2 的读者也改用评测侧的统一 `read_evidence`，四组读者读原文的入口相同。
- **C、D、P：** 已有结果保留。读者仍只经库读原文，与 ref1 设计时的前提一致；比较前核对来源范围与版本，标明可比边界。是否需要补跑另行确认。
- **f2-A3：** 保留为全材料访问参照。〔待定，暂缓〕读者怎样在它的 k10、k20、k30 备份上作答：其旧锚点使用库内 ID 与行号，可以直接用已实现的 `anchored read_evidence`（c6b2621），也可以按可审计的规则把旧引用转换成来源 ID 后用统一工具。结果单独标注，不与 f3 混为同条件实验。

## 9 结论的边界
