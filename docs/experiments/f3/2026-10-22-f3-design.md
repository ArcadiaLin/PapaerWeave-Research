## 1 为什么有 f3

f1、f2 的写者从第一个会话起就能看到全部 30 篇论文与代码，可以绕过库直接读、grep 尚未入库或别人建过的论文，库不是写者之间唯一的通道。主流的记忆评测（LongMemEval、MemoryAgentBench）都按时间顺序把材料逐步交给被测系统；我们的设定更依赖这一点，因为要检验的正是后来者能否经库发现、核查并接续前人的贡献。

f3 调整写者的信息条件，并统一证据引用与读者来源访问协议：**每个写者带着当前任务进入自己的工作空间，用本次任务提供的材料与共享库中的历史贡献完成工作，再把结果提交回共享库。** 不预先提供全套论文，不禁止核查已开放的原文，不限制 agent 使用正常的文件与 shell 工具。

f3 要检验的是：

> 局部任务持续带来新材料时，不同的存储方案能否让后来的写者发现、核查并接续此前的贡献，以及为此付出多少成本。

不研究协调协议：不引入协调者或跨写者的消息通道（10-22 讨论）。f2-A3 保留为全材料访问参照，不是协调组。

## 2 写者能访问什么

〔已确认 2026-10-22〕每个会话有三个入口，四组相同：

| 入口 | 内容 |
| --- | --- |
| 当前任务 | 任务文字，以及本次直接提供的来源 ID |
| 私人工作空间 | 本次会话的草稿、脚本、下载材料与会话文件；每次重新开始，同一身份下次也不继承 |
| 本组的共享库 | 此前各写者的贡献：记录、产物及其来源引用 |

- 沙箱不挂载论文目录与代码目录，断网（V3 §7 第 5 条照旧）。
- 共享库是写者之间发布与获取贡献的唯一通道；私人工作空间不是公共成果库。
- 现状：A3、A2、A4 的私人工作目录本来就按身份保留（`<组>/writers/<身份>/work`）；f3 改为每会话全新目录，也不再挂载 `papers/` 与 `code/`。A0 不同：它的 `/work` 是共享仓库的工作树，所有写者共用一份，会话之间不清理（f1 跑完时仓库里留着未提交的改动），A0 写者没有私人目录。

### 2.1 每会话重新开始，只继承共享库

〔已确认 2026-10-22〕四组每个新会话使用全新的本地工作目录，pi 的 cwd 为 `/work/`。即使沿用同一写者身份，也不继承上一会话的私人下载、草稿、脚本或未发布文件；home 中的会话记忆同样不得跨会话继承，运行所需固定配置照常提供。共享库持续保留。

| 会话开始与交接 | A0 | A3 / A2 | A4 |
| --- | --- | --- | --- |
| 开始时的工作空间 | 全新 `/work/`，在 `/work/store/` 取出共享 Git 最新已发布状态 | 全新 `/work/`，连接已有 PaperWeave | 全新 `/work/`，连接已有 Graphiti |
| 获取来源 | `read_source` 下载到本次 `/work/sources/` | 同左 | 同左 |
| 发布贡献 | 选择文件并 Git 提交 | 通过系统接口提交记录与产物 | 写入 episode |
| 下一会话继承 | Git 已发布文件与历史 | 库中已发布记录、来源引用与产物 | 库中已发布 episode |

`read_source` 将指定来源的固定版本下载到本次 `/work/sources/`，返回本地路径、版本、行数与内容哈希；论文保存为 Markdown，代码保留仓库内目录结构。agent 使用 pi 自带的 `read`、`grep` 与 shell 阅读和处理。四组采用相同的下载行为，只有主动请求的已开放材料才落盘，不预装全部语料。

**下载不等于发布，下载原文不自动传给下次会话。** 此规则替代此前“只返回上下文、不自动存文件”与“私人目录按身份跨会话保留”的约定：

- A0 可以主动把全文提交进 Git，之后其他会话就能直接读、grep；这是文件方案的正常能力，不禁止，也不强制。
- A0 也可以只提交笔记及来源 ID、版本和可选的证据定位；后来者据此调用 `read_source` 重新获取原文，不必要求前人先提交全文。
- A3、A2 从库中取得来源引用后，同样调用 `read_source` 获取固定版本原文，不依赖前人的本地文件或以 PW 内部材料 ID 定位论文；也可以用 PaperWeave 的 `read_evidence` 按来源引用直接读几行（第 4 节第 4 条）。需要产物文件时调用 `checkout`。
- 来源服务不自动向任何共享库写入全文、来源 ID、摘要或引用。共享内容由 agent 自己发布，计入实际存储与读写成本。

### 2.2 A0 的 Git 发布与会话归档

〔已确认 2026-10-22〕A0 共享的是已发布的 Git 历史，而不是上一会话的未提交工作树。每个会话在全新工作目录中取出公共仓库的最新已发布状态，不需要按身份维护长期工作副本。

〔提议〕发布操作沿用 Git：agent 自己选择文件并执行 `git add <选定文件>`、`git commit`；框架在会话正常结束时把新提交同步到共享仓库（2026-10-22 定，见工程文档 B4），不代选文件、不自动执行 `git add -A && git commit`。约定文档明确说明：**本次需要共享的记录与产物写入 `/work/store/`，选择对应文件并提交；私人下载与草稿留在 `/work/` 的其他目录。** 要求发布的是本次贡献，不是整个工作空间，也不要求提交读过的全文。其他组同样说明本地工作与调用各组接口发布的区别。

〔已确认 2026-10-22〕会话结束时，未发布内容保存在评测快照或归档中供审计，不自动挂给后续会话，也不向原身份提供跨会话恢复入口。归档不属于 agent 可查询的共享库。未提交内容计为**未发布贡献**；已发布且正确的内容后来消失，才计为已积累知识的流失，不能把会话目录清理记成存储方案的知识流失。

新会话与基础设施中断后的同一会话重试必须区分。〔已确认 2026-10-22〕中断后库没变时从全新目录重跑，不恢复该次现场；库已变时不重跑，照实记账。细则见 `docs/experiments/f3/2026-10-22-f3-implementation.md` 第 2.4 节。

## 3 材料怎样随任务提供

### 3.1 每类会话直接提供的材料

〔提议〕清单由任务文字预先确定，不依据读者题目或答案选择：

| 会话（数量） | 直接提供 |
| --- | --- |
| build（28）、build-overlap（7） | 指定的那一篇论文 |
| compare（4） | 指定的两篇论文 |
| update（3） | 指定论文的新旧两个版本 |
| verify-own（3） | 该论文；不额外提供代码 |
| verify-later（3） | 被核查的论文；后来的相关论文从共享库发现 |
| note-i6（2） | 该论文及其固定 commit 的官方代码仓库 |
| note-i1（2） | 不直接提供，从共享库选型 |
| leaderboard（14）、summarize（4） | 不直接提供，从共享库发现输入 |

“提供”是在任务中给出可读的来源 ID，不预先挂载材料；agent 调用 `read_source` 后，指定材料才下载到本次会话的 `/work/sources/`。

### 3.2 开放、历史与未开放

〔提议〕

| 状态 | 写者怎样知道 | 能否读 |
| --- | --- | --- |
| 本次任务直接提供 | 任务给出 ID | 全文 |
| 此前已开放 | 从共享记录、产物引用或本次会话已经获取的材料中得知 ID | 全文 |
| 尚未开放（含未来版本） | 不提供 | 不能读，即使猜中 ID |

- 开放时间由计划表决定，四组一致：种子材料在起点开放，其余材料在第一次直接提供它的会话开始时开放，此后一直可读。
- 开放与某组是否写进了库无关。“已开放”是来源服务允许读取；“已贡献进库”是写者实际留下了别人能发现的记录、引用或产物。来源服务不替写者把来源 ID、摘要或记录发布进库。
- 推论：只有 2 个代码仓库（Autoformer、CATS，随 note-i6）会开放；f2 中写者能看到 27 个仓库。

## 4 来源服务 `read_source`

〔已确认 2026-10-22〕**一个独立的 MCP 服务，模拟从 arXiv、代码托管站等外部来源取材料**：它不属于任何一组的库，四组相同，只是按计划表决定材料何时“发表”。与真实的 arXiv 不同，它不能检索、不能列目录，这是有意的限制：发现材料必须经库完成，否则写者可以在“arXiv”上直接搜，绕过库。论文中说明这一点。

〔提议〕接口：

```text
read_source(source_id)  # 下载固定版本来源到本次会话的 /work/sources/
```

- 返回来源 ID、固定版本、本地路径、内容哈希及论文行数；代码返回本地根目录与清单文件路径，清单记录文件路径、行数和哈希。全文不塞入 MCP 返回，由 agent 用文件工具按需读取；各组同一下载与返回格式。
- 可以按 ID 读已开放材料的全文，不要求所读行已被锚点覆盖。这是四组写者的入口；读者不用它，另有只读锚点所在块的工具（第 6 节）。
- 不提供全部材料的列表、跨论文全文检索或相关推荐；不抽取、不总结、不判断。
- 下载后的代码仓库可以列出仓库内的文件，但不能借此枚举别的仓库。
- 拒绝（未开放、不存在、格式错误）逐次记录。
- 下载只写入本次会话的 `/work/sources/`，不写入 `/work/store/` 或其他共享库。同一会话内重复下载同一来源时返回已有路径，并报告本地副本的哈希是否仍与来源一致；路径规则在实现前固定，四组一致。
- 记录来源请求、下载字节数及本地副本复用情况；后续文件读取由会话轨迹审计。下载字节数不等于模型实际读到的内容量，也不等于输入 token 成本。

细节：

1. 〔已确认 2026-10-22〕**外部来源 ID（source_id）：** 论文用带版本的 arXiv 编号（如 `2205.13504v2`），代码用 `<仓库>@<commit>`：稳定、不编码答案或开放顺序、不暴露宿主机路径。题库已经在用这种写法；A0 的约定只用它命名论文目录（`papers/<arXiv id with version>/paper.md`），位置写作 `<章节>::<起>:<止>`，不带来源 ID，需要改（第 7 节）。
2. 〔已确认 2026-10-22〕**形式：** 独立的 MCP 服务，四组都接（A0 原本不接 MCP，只加这一个只读工具，不改变“文件 + Git”的本质）；工具说明四组逐字相同。
3. 〔提议〕**返回大小与文件交付。** MCP 只返回简短的下载结果，控制在 pi 的 20 KiB 截断阈值以内；大代码清单放在本地文件中，不分页返回全文。pi 自带文件工具的截断与上下文行为保持不变。来源服务只将请求的材料交付到本次会话的 `/work/sources/`；不得借文件交付访问其他会话或身份的目录，或枚举未请求的材料。
4. 〔已确认 2026-10-22〕**写者读原文的入口。** 四组写者都通过 `read_source(source_id)` 下载来源，再用普通文件工具阅读或搜索。A3、A2 另保留 PaperWeave 的 `read_evidence`（被测系统的一部分），改为按 `<source_id>::<locator>` 读：文字取自来源目录中的固定副本，返回所引的行并附章节名，可用 `at` 按旧视图解析，也能读产物文档（输入写作 `art_xxxx::<起>:<止>`；这只是读取的输入，不能写进 anchor，见第 4.1 节）。system 不导入 eval：system 配置一个只读的来源目录，按来源 ID 与内容哈希解析，目录中只放已开放的来源（与现在的材料根目录同一做法），所以 `read_evidence` 能读的都已开放，信息上不多于 `read_source`。证据引用不再使用 PW 内部论文／Material ID。读者的入口见第 6 节。当前实现仍使用旧机制，需要修改，不能只改提示词。
5. **来源持久性。** 固定版本原文由来源服务持久持有，本次工作目录只是下载副本。相同 `source_id` 必须对应相同内容及规范化格式，并可用哈希核验；不能每次重新转换出不同行号的论文文本。证据解析不依赖上一会话的文件，也不要求 PaperWeave 另存一份论文副本；PaperWeave 的提交校验与 `read_evidence` 都经第 4 条的来源目录解析。

### 4.1 anchor：来源 ID 与可选定位

〔已确认 2026-10-22〕**anchor 是可解析的来源引用，不限定为行号范围。** 语义形式为：

```text
<source_id>[::<locator>]
```

- `source_id` 必填，与 `read_source` 使用的是同一个外部来源 ID，不是 PW 自动分配的节点 ID，也不是本次下载的本地路径。
- `locator` 可选，标识来源内部的位置。省略时指向整个来源。
- 〔已确认 2026-10-22〕**f3 只实现行范围定位：** 论文写 `a:b`，代码写 `<文件路径>::a:b`；章节名照旧只作提示（`<source_id>::<章节>::a:b`）。只到文件或只到章节的定位，对读者按“没有定位”处理，不放行段落；grounded 记录“必须带定位”指行范围。文件、章节、页面片段等定位留作扩展，须先定义各自的解析方式与放行范围。
- 〔已确认 2026-10-22〕**定位的要求是 PaperWeave 的设计特色，不是各组共同的说明。** 两项检查分开：
  - **记录有效性**（A3、A2 都启用）：grounded 记录的每条 anchor 都须带可解析的行范围定位，拒绝只写来源的 anchor（Content 的 anchor 现在就是必填字段：`system/src/paperweave/model/schema.py` 中 Content 的必填项为 `paper`、`anchor`、`description`）。f2 中的行号越界校验也是两组都有。
  - **修订约束**（只有 A3 启用）：修改 grounded 记录时须另附依据 anchor 与理由。A2 的 `revision` 消融（`eval/baselines/a2_mcp.py`）只去掉这一条，不影响记录有效性。
  - A0、A4 的说明不另外要求定位；各组边与产物中的引用都可以只写来源。
- 位置存在不代表它支持所述结论，语义正确性另外评测。
- 〔已确认 2026-10-22〕没有定位的 anchor 对读者不放行任何段落（第 6 节）：它说明了来源，但没有把读者带到来源中的某处。由此造成的读者差异是被测量的组间差异；各组无定位 anchor 的比例作为指标报告。
- 当前 artifact 不作为证据来源，不引入 `pw:` 分支。产物的存储、依赖关系与 `checkout` 不因此取消。

以下是语义示例；分隔符、转义与各来源类型的定位语法须在实现前固定，避免路径和 URL 歧义：

```text
2205.13504v2                         # 整篇论文
2205.13504v2::210:245                 # 论文中的行号范围
repo@<commit>::src/model.py          # 固定版本仓库中的整个文件（f3 中对读者不放行段落）
repo@<commit>::src/model.py::30:48    # 文件中的行号范围
<网页快照ID>::#experimental-results  # 固定网页中的片段（扩展示例，f3 不实现）
```

网页等来源是可扩展方向，不要求 f3 实现网页支持；本轮先覆盖论文与固定版本代码仓库。

写者在 graph-doc 中直接填写来源引用，例如：

```yaml
# Paper：声明它的来源 ID
source: ["2205.13504v2"]

# Content：所属论文用库内 ID，证据用来源引用
paper: paper_0001
anchor: ["2205.13504v2::210:245"]
```

`paper` 仍是记录所属论文的库内 ID；`anchor` 独立说明证据的外部来源与可选位置。agent 从任务或 `read_source` 返回中取得准确来源 ID，不猜内部 Material ID，不用私人文件路径代替来源 ID。

提交校验从“当前论文材料中的裸行号”改为“来源可解析；若给出定位，该位置存在”，并核对 anchor 的来源是记录所属 Paper 声明的来源之一，或允许的关联来源（如官方代码）。代码文件必须定位到对应固定 commit；关联来源的校验规则在实现前固定。不能自动补写 agent 未提供的局部证据定位。

**论文与来源 ID 的对应**〔已确认 2026-10-22〕：

- 同一论文的不同版本是不同的来源 ID（`2205.13504v1` 与 `2205.13504v2`）。版本先后从 ID 读出：arXiv 编号相同时，版本号大者更新，系统按这条规则比较，不另建版本表。代码的 `<仓库>@<commit>` 不排序；f3 只开放 2 个仓库，不处理代码的新旧版本。
- Paper 由写者声明自己的来源 ID（`source`，取代现在的 `material` 字段）；update 任务中写者把新版本加进去。运行器不预先把对应关系放进库：来源服务与框架都不替写者发布（第 2.1 节）。
- 过时检测改按来源 ID：记录或产物引用的来源，其 Paper 已声明同一编号的更新版本时，标为被新版本取代（取代现在 `Material.superseded_by` 的判断）。

写者的读取流程：从共享记录或产物中发现 anchor，取出 `source_id`，调用 `read_source` 获取固定来源，再按 locator 用文件工具定位；没有 locator 时由 agent 自行搜索和阅读。对写者，anchor 用于定位，不是全文访问的权限清单；对读者，库中记录的 anchor 就是可读段落的放行名单（第 6 节）。

### 4.2 旧数据的映射（评测侧）

〔已确认 2026-10-22〕种子与 f1、f2 的历史数据用库内 ID 引用论文（如 `paper_0001::Datasets::265:273`，A3 种子排行榜与 A0 的 `a0-leaderboards.md` 都是这种写法）。f3 不为旧格式重跑，也不在 system 中兼容旧格式：评测侧在建库时把种子转换成新格式，再放进 A3、A2 的起点库与 A0 的起点仓库（A0 的起点仓库由 `eval/src/pweval/harness/a0_seed.py` 从种子渲染，其中的位置 `<章节>::<起>:<止>` 同样补上来源 ID）。种子在题库 `~/pw-lab/probes/seed/`，原文件不改；转换一次，结果连同对应表冻结在题库 `seed/f3/`，可复核（工程文档 B7）。这是评测的调整，不进入论文。

- **对应表按材料建，不按论文 ID 建：** 材料路径本身带版本（如 `papers/2106.09305v3/paper.md`），材料到来源 ID 的对应可以机械得出。一个 `paper_xxxx` 在有多个版本的库中对应多个来源 ID，按论文 ID 映射会把旧证据映到新版的行号上。
- **转换覆盖：**
  - Paper 的 `material` 改为 `source`；
  - Content 的裸 anchor，按它 `FROM` 边上的材料补上来源 ID；
  - 边的 anchor，按边上的 `material_ref`；
  - 产物 `USED` 边的定位，按边上的材料；
  - 产物文档正文中的 `paper_xxxx::…`，按该版文档写入时论文的材料解析。
- 种子只有单一版本，转换直接；多版本只出现在 f2 等历史库中，f2-A3 暂缓，但按上述规则处理。

### 6.2 读者的 `read_evidence`

- 〔已确认 2026-10-22〕名为 `read_evidence`，四组的工具与说明逐字相同。A0、A4 没有 PaperWeave 服务，所以它由评测侧提供。

〔提议〕格式：

- **输入：** `read_evidence(refs)`，每条写作 `<source_id>::<locator>`，如 `2205.13504v2::210:245`、`<仓库>@<commit>::src/model.py::30:48`。
- **放行：** 落在某个放行段之内的任何子区间都能读，不要求与记录的锚点逐字相同；返回所在整块的文字，带行号，表格给整张表，论文附所在章节名；直接放在返回中，不落盘。
- **拒绝：** 落在放行段之外、只写来源没写定位、未开放的来源，都拒绝；前两种列出该来源能读的行段。这份清单是库中锚点的投影，不多给信息。
- **大小：** 单条最多 400 行，单次返回不超过约 16 KiB，留在 pi 的 20 KiB 截断阈值以内（f2-A3 的 `read_evidence` 有 18/182 次被 pi 截断，只有 5 次回读了全文）。〔已确认 2026-10-22〕授权与交付分开：放行范围不变；扩到的整块超过限制时不扩块，只返回请求的子区间；子区间仍超限时返回不超限的前段，并注明“该块为 a:b，从第 x 行继续请求”。放行段内的任何子区间本来就能读，分页不需要新规则。正式语料 5662 个块中有 5 个按带行号的格式超过 16 KiB（最大约 22.8 KiB，都是大表），没有超过 400 行的。一次请求多条引用时，放不下的整条标为“未读，请再调用”，不从中间截断。
- **文字来源：** 来源服务持有的固定副本（第 4 节第 5 条），行号与写者所见一致。
- **记录：** 每次请求、放行或拒绝、返回的块与字节数。

- **核心证据机制（`system/`）：** anchor 的解析、持久化、读取投影与提交校验改用外部 `source_id` 加可选 locator，替代 PW 内部材料 ID／裸行号；grounded 记录的定位校验；Paper 的 `source` 字段取代 `material`；过时检测按来源 ID 的版本规则；提交校验与 `read_evidence` 经只读来源目录解析（第 4 节第 4 条）。system 不兼容旧格式。该项属于 `system/` 的机制变更，不只是 eval 提示词修改；保持 system 与 eval 不互相导入的边界。
- **旧数据映射（`eval/`）：** 材料到来源 ID 的对应表，建库时按第 4.2 节转换种子的 Paper 字段、Content 与边的 anchor、产物定位与正文引用。

## 9 结论的边界

- 关注贡献是否保留、产物是否被复用并正确更新、变化是否被发现，以及维护与后续使用的成本；不以 `checkout` 或 `read_source` 调用多为成功。
- 本设计调整写者信息条件、证据引用机制与读者来源访问协议，不检验协调协议，也不声称与协调系统等效。
