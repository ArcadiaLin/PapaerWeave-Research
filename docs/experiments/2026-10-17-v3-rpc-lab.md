# V3 RPC 实验室：边测边改（2026-10-16 夜 — 10-17）

> **状态：** 进行中。目的不是出结果，而是用默认配置的通用 agent 反复跑 V3 工具，找出工具说明、错误提示与写入规则中让 agent 卡住或写错的地方，随即修改，再跑。每轮记录现象、原因与改动。实现上的决定逐条记在本地决策日志 `tmps/2026-10-16-v3-impl-decisions.md`（不入库），设计层面的结论回写到 [数据模型 V3](../designs/v3/data_model.md) 与 [工具 V3](../designs/v3/tools.md)。

## 设置

- **系统：** `system/`（V3，见提交历史 `01a2c44` 起）；V2 留在本地 tag `v2-pilot3`。
- **库：** 容器 `neo4j-lab`（`neo4j:ubi10`，bolt 7695），每轮实验前可清空（`tmps/rpc-lab/reset_lab.py`，只允许 7695）。不连 neo4j-e09 / neo4j-test / neo4j-t1。
- **材料：** `~/pw-lab/data/papers/<arXiv 号>/paper.md`，复制自 `data/raw/t1-pilot-corpus/papers/`（11 篇时间序列预测论文）。工作目录中有一份同样相对路径的副本，agent 写的 `material` 就是它读的文件。
- **写者：** pi 1.2.0，默认系统提示与内置工具，`--mode rpc`，模型 qwen3.8-27b（sglang，局域网）。PaperWeave 经 MCP 以 `direct` 方式列出 10 个工具（`search get traverse read_evidence checkout commit log show diff as_of`）。每个写者一个工作目录（`~/pw-lab/runs/<名字>`）与登录身份（`PAPERWEAVE_USER`）。实验只控制工作目录与任务文字。
- **驱动：** `tmps/rpc-lab/driver.py`（`new` 建目录，`run` 跑一次会话并把事件写到 `.pi/rpc/<时间>.jsonl`、摘要写到 `<时间>.md`）。任务文字在 `tmps/rpc-lab/tasks/`。

## 测试类型

| 类型 | 任务 | 看什么 |
| --- | --- | --- |
| 从零建库 | 一篇论文入库（2–3 篇依次） | 能否写出合法的 graph-doc；查重与修订规则是否可承受；锚点是否落对 |
| 维护 | 改一处错误、补一条边 | 能否找到要改的节点；`set`/`delete`/`confirm.revise` 是否用对 |
| 读取探针 | 只用库回答问题 | search / traverse 是否够用；答案是否带 id 且正确 |
| 多会话接力 | 不同写者轮流写同一个库与产物 | 重复与误合并；产物检出/检入；过期提示 |

## 轮次记录

（按时间顺序追加。）

### 第 1 轮 b1-build：空库录入 PatchTST（writer-a）

- **结果：** 500 秒、26 次工具调用（PaperWeave 11 次，其中 `commit` 4 次），一个提交写入 54 个节点、239 条边（另有名称键与材料节点，共 94 个节点）。写者没有用 `checkout new`，只照 `commit` 说明中的示例写出了整份 graph-doc（约 34 KB）。
- **卡住的地方与改动：**
  1. 空库上 `search` 报全文与向量索引不存在，`log` 报没有 `main` 分支：索引与版本记录原先在第一次提交时才建。改为 MCP 服务与命令行启动时建立（可重复执行）。
  2. 同一个 `$name` 定义了两次，报 YAML 重复键。写者误以为要“按依赖顺序排列节点”，重写了整份文件（凑巧也去掉了重复）。改为：YAML 错误带行号；重复键时说明每个 `$name` 只定义一次。
  3. Paper 没写 `material`，所有锚点报“桩论文没有材料”。写者到工作目录之外（`~/pw-lab/smoke/`）翻到冒烟测试的 graph-doc 才知道该写什么。改为：错误中直接说明怎样写 `material`（并删除了实验室中的冒烟文件）。这是一次绕过中间件的读取，按规定只记录、不阻止。
  4. 写者写了 `arxiv:2211.14730v2`。带版本的标识会让后来写 `arxiv:2211.14730` 的会话查重落空，造成同一篇论文两个节点。改为：arXiv 标识不带版本号，带了就阻塞并给出改法（版本由材料表达）。
  5. `RELATES_TO` 的类型提示对 Method → Issue 建议 `BROADER`，但 `BROADER` 要求两端同 kind。提示改为遵守同 kind 要求。
- **锚点抽查（全部 25 条 Content）：** 多数锚点落在对应的段落或表上。但引用单行的锚点有 3 处差一行：两处落在空行上（`45:45`，摘要在第 46 行），一处落在只有列表符号的 `- •` 上（`55:55`，内容在第 56 行）。可能的原因：pi 的 `read` 不显示行号，写者要自己数，单行锚点没有容错。改为：锚点范围内一个词都没有时阻塞，并给出最近的有字的行。
- **观察（未改）：**
  - 写者为 PatchTST 同时建了 Method 与 Model（`model_0001`，别名 PatchTST/42、/64），并让 12 组实验都 `EVALUATES` Model。数据模型的本意是变体写在实验说明中，评测对象是 Method。说明中没有讲清 Method 与 Model 的分工。先观察 b2 是否重复这一做法。
  - 写者另建了两个组件 Method（Time series patching、Channel-independence），用 `RELATES_TO` 连到 PatchTST；数据模型允许这样做。
  - 写者建了 Issue（数据模型说当前论文表单不写 Issue，但工具说明并没有禁止）。
- **给 b2 的库：** 用命令行重放 b1 的 graph-doc（去掉 arXiv 版本号），结构与 b1 相同，来源记为 `cli`。

### 第 2 轮 b2-build：在 b1 的库上录入 Autoformer（writer-b）

- **结果：** 397 秒、22 次工具调用，一个提交新建 56 个节点、142 条边，并改了 3 个已有节点：给 `method_0006`（Autoformer）补了说明与组件关系，给 `dataset_0010` 补了 `FOR_TASK`，给 PatchTST 论文补了 `CITES` → Autoformer 论文。库里没有重名节点：b1 已建的 Autoformer、Informer、ETT 系列等都被复用，11 个新节点都对候选做了判断，没有误合并。实验评测的是 Method（73 条 `EVALUATES` 指向 Method，只有 b1 的 12 条指向 Model），但 b2 仍为 Autoformer 建了一个 Model。
- **卡住的地方：** 第一次 dry run 返回 20.5 KB、414 行。pi 截断了输出、存到临时文件，写者用 `sed` 在文件里翻找查重候选。内容包括：
  - 17 条锚点错误，都是同一个原因（Paper 没写 `material`）。这次写者按新提示一步就改好了。
  - 11 条查重。每条 3 个近似候选，多是不相干的方法：Reformer 的候选是 LogTrans、Informer、FEDformer。每个候选还带 200 字的描述，改法说明每条重复一遍。
  - 9 条方向错误：Claim → Experiment 的 `SUPPORTS`。写者删掉了这些边；它在实验一端另写过同样的 `SUPPORTS`，所以没有丢信息。
- **改动：**
  1. 同一条错误只报一次，`at` 列出各处位置。
  2. 查重候选一行一个：kind、名称、描述开头 100 字与命中的通道。改法说明缩成一句。
  3. 方向写反、而反过来合法时，直接给出从另一端怎样写。
  4. 查重的近似候选设向量阈值 0.84（Neo4j 的 $(1+\cos)/2$，约合 $\cos = 0.68$，与 Graphiti 的 0.6 相近）。依据是在 b1 库上的侦察：b2 的 15 个新节点与 5 个人造的真重复，真重复的最高近邻在 0.851–0.911，不是重复的近邻多在 0.76–0.84；高于阈值而不是重复的有两例（Auto-Correlation、Transformer 对 Autoformer，属于相关概念）。样本小，暂定。
  5. 两边都有唯一命名空间（`arxiv`、`doi`、`s2`）的标识而互不相同时，不列为近似候选：两篇 arXiv 号不同的论文不必再判断。
- **效果：** 用 b2 的初稿在同样的库（b1）上重做 dry run，返回从 20.5 KB / 414 行降到 5.0 KB / 99 行，查重候选从 45 个降到 3 个（Auto-Correlation、Series decomposition block、Transformer 各对 Autoformer）。
- **b1 的重放：** 新的无字锚点检查拦下了 b1 的 4 处单行锚点（3 处 `45:45`、1 处 `55:55`），按提示改为 46、56 后重放。这正是第 1 轮抽查发现的那几处。

### 第 3 轮 b3-build：在 b1、b2 的库上录入 TiDE（writer-c）

- **结果：** 568 秒、34 次工具调用。写者一开始就用了 `log`，又用 `search`、`get` 查了已有节点，第一次 dry run 就通过，一个提交新建 27 个节点、94 条边。查重没有给出任何候选（新建的 N-HiTS、S4、M5 在库里确实没有）。已有的 6 个 Transformer 基线、DLinear、LSTM、DeepAR 与 ETT 系列都被复用；给 PatchTST、Autoformer 两篇论文各写了一条 `CITES`，说明了引用的用途。
- **发现：早写者的建模习惯被照抄。** b1 把 PatchTST 的实验都指向 Model 节点（`model_0001`）。b3 比较 PatchTST 时也指向 `model_0001`（3 条 `EVALUATES`），又给 TiDE 建了 `model_0003`（“Trained TiDE models … hyper-parameters”）。结果 TiDE 作为 Method 被评测 1 次、作为 Model 被评测 7 次。第 2 轮后改过的 Model 说明没能压过库里的先例。按 `EVALUATES → Method` 做排行榜时，会漏掉 PatchTST 与 TiDE 的大部分结果。这是无协调写者下的一种退化：没有错误，每次写入单独看都合理，约定却在接力中漂移。
- **其他问题与改动：**
  1. `search` 的 `kind` 被传成逗号分隔的字符串 `"Task,Issue,Model"`（sglang 对列表参数的老问题），被拒。改为：声明为字符串数组的参数收到不是 JSON 的字符串时，按逗号切开。
  2. `RELATES_TO` 的类型提示报到了 b2 写的旧边上（这次没写的 `method_0006` 的边）。原因是检查覆盖了被触及节点的全部出边。改为只检查本次写入或改动的边，以及 kind 变了的节点的边。
  3. 提交结果的计数（41 个节点、108 条边）与 dry run（27、94）不一致：前者算进了名称键与材料节点。写者为此调了两次 `show`。改为两者同一口径。
  4. 实验评测一个没有外部标识的 Model 时给出警告，指出应改评测哪个 Method（该 Model `IMPLEMENTS` 的那个）。这只是提示，不阻塞。库里已有的 Model 用法留给维护轮或后来的写者处理，看警告能否让约定收敛。

### 第 4 轮 m1-maintain：改回被改错的主张，补一条跨论文的边（writer-d）

- **准备：** 以 writer-x 的身份用命令行改错 `claim_0001`：PatchTST 胜过 DLinear 的数据集从“large datasets (Weather, Traffic, Electricity) and ILI”改成“small datasets (ETTh1, ETTh2, ETTm1)”。改动附有看似合理的修订理由（“re-reading the results paragraph”）与锚点（commit_000004）。任务只说“读者报告这条主张看起来不对”，不给 id；另要求补上 PatchTST 主实验与 Autoformer 的 SOTA 主张之间的联系。
- **结果：** 94 秒、10 次工具调用，没有错误。写者用 `search` 找到主张，用 `read_evidence` 读第 166 行，发现与原文不符；再用 `log node: [claim_0001]` 与 `show` 找到 writer-x 的修订。随后一个提交：`set` 改回原文的说法，`confirm.revise` 的理由写明原文怎么说、哪次提交改错了；并新建 `exp_0001 OPPOSES claim_0010`，带 Table 3 一带的锚点与说明。
- **观察：**
  - 有据层的修订路径（`set` + `revise` + 历史可查）在这一轮完全走通：找错、溯源、改回、留下理由。
  - 写者给新边另写了一条 `revise`（边上已有锚点，不需要），无害。
  - `OPPOSES` 的语义可以商榷：Autoformer 的“state of the art”是相对它当时的前人方法说的，后来的论文超过它并不构成反驳。这条边是任务文字诱导出来的；它属于解释层，库按设计不裁决。时间性的主张容易被标成 `OPPOSES`，这一点留给评测的标注规则。

### 第 5 轮 p1-probe：只用库回答两个问题（reader-e）

- **设置：** 工作目录里没有论文副本。第 1 题（ETTh1 上作为基线评测的方法及所在论文）的标准答案在开跑前用 Cypher 从库里算出，共 24 个（论文，方法）组合（`~/pw-lab/replay/p1-gold-q1.txt`）。第 2 题（关于 Transformer 预测模型的主张及支持它的实验）是开放题，人工核对。
- **结果：** 135 秒、8 次工具调用（`search` 2、`traverse` 1、`get` 5）。第 1 题 24 个组合全部答出，没有多答。路径是 `traverse` 从 `dataset_0002` 沿 `USES` 反向走到 13 个实验，再 `get` 取各实验的 `EVALUATES` 边。第 2 题按主张对象分组，支持实验与库中的 `SUPPORTS` 一致，并指出了 `claim_0010` 被 `exp_0001` 反驳。
- **读者看到的库内问题：**
  - PatchTST 在 TiDE 的实验里作为 `model_0001` 出现。读者为此把 PatchTST 写成 “method_0003/model_0001”，自己把两个节点对上了，答案没有出错。
  - Autoformer 的 `exp_0015` 的说明提到 LSTMa，库里却没有对应的 `EVALUATES` 边。
  - 7 条 PatchTST 主张没有 `ABOUT` 边。
- **读取工具的观察：** `traverse` 的紧凑投影截断了出边（`_more: EVALUATES: 3`），读者随后用 `get` 补齐，一共多了 5 次调用。目前可以接受。
