## 1. 评测要回答的问题

### 1.1 主场与边界

最强的反驳是：**一个 Agent 用 markdown 文件加 git 就够了。** 在单个 Agent、单个项目、几十篇论文的场景里，这个反驳大概率成立；即使数据库有优势，也可能抵不过构建成本。评测不把主场设在这里。我们把这个场景作为边界条件（$K=1$）如实报告，不回避。

数据库思路站得住的场景是：**许多互不协调的 Agent 或 session，长期往同一个共享库里写入，也从中读取；读者往往不在写入现场。** 这正是数据库的传统存在理由：数据共享、长期存在、多写者多读者、需要完整性。在这种场景下，无约束的积累预计会出现五类退化。前四类在写侧：

- **重复与误合并（C1）：** 同一个对象被不同写者写成多个实体，或者不同对象被并成一个；
- **悬空（C2）：** 引用指向不存在或已被改动的对象，产物缺少条件与输入，复查不了；
- **未察觉的冲突（C3）：** 不同写者对同一结果给出不同读法，后写的静默覆盖了先写的；
- **过时（C3）：** 产物所依据的材料或记录已经修订，却没有人知道它需要复检。

第五类在读侧：

- **找不到（C5）：** 写者按自己的目的、措辞和粒度存放内容，换一个目的的读者找不到。

下游读者拿到的答案会因此出错，而且错得不显眼。

### 1.2 中心命题

| 命题 | 内容 | 怎样算被证伪 |
| --- | --- | --- |
| **T1 退化（核心）** | 写者数与写入量增长时，A3 的库健康度与下游正确率退化得明显比各对照组慢 | 在可负担的规模内，A3 的退化斜率不显著优于 A0 |
| **T2 摊销** | 构建成本从使用阶段前移到构建阶段，并在许多使用者之间摊销 | 盈亏平衡点 $N^*$ 在合理的使用者数内不存在；或者对照组拿到同等预计算预算后获得同等收益 |
| **T3 能力平移（可选）** | 结构化访问能缩小弱模型与强模型的差距 | 在模型强度扫描中，用与不用 PaperWeave 的差距不随模型强度变化 |

**[已商定]** T1 是主实验。T2 用 T1 时间线上的成本账本回答，不另起实验。T3 只在资源允许时进行，做法是换模型重跑 T1 与 L4。

C4（项目视图与版本历史）不单独成节，而是作为 T1 时间线上的事件来评测（§2.3）：

- 写者群体之间的隔离就是分支；
- 撤回或修订一条记录后，查哪些产物受影响，就是历史查询与影响查询；
- 项目成果回流到共享库，是多写者写入的一条路径。

| 主张（出处） | 证据 | 位置 |

### 1.4 评测原则

以下原则沿用项目既定规则：

- **先评存储层的支持能力。** 下游任务分数是应用证据，不是唯一的度量。正确率、交互与执行成本、可扩展性和维护行为都要报告。
- **能力对比要可操作。** 区分原生支持、经组合支持、需要外部推理才能支持三种情况。特性表本身不构成证据。
- **宣称与核验分离。** 论文的宣称、仓库中的观察、运行成功和实验复现是不同的发现；证据不足时保留不确定性。
- **两类评测分开报告。** 一类是在同一份已构建知识上的受控对比，隔离使用阶段（§5）；另一类是构建加使用的全流程对比（§4）。
- **公平对照。** 各组访问同样的材料，使用同一个通用 Agent（默认配置的 pi）、同一个模型和同样的预算。评测审计绕过 PaperWeave 直接读源材料的行为，但不禁止。
- **主指标跨组可比。** 各组的存储形态不同（文件、向量、记忆、图），库健康度在部分组上无法直接定义。因此跨组比较以下游探针为准，库健康度作为诊断。探针正确率混有读者能力、模型记忆与绕过行为，必须配合闭卷下限、神谕上限与逐题归因报告（§4.3）。
- **先冻结后实验。** 写者任务、探针、金标准、rubric 和筛选规则在正式实验前冻结，不按正式结果挑题。负载要包含复用有利、收益不明显和可能有害的任务。
- **主张与负载对齐。** 主张只针对多写者、跨论文、跨 session、条件敏感的负载。在通用单轮问答上与 RAG 打平，不构成反驳；我们也不在这类任务上主张提升。
- **评测材料公开。** 任务定义、探针、金标准、rubric 和运行轨迹随论文公开。AgenticScholar 没有公开评测集，这是它被质疑的一点。

## 2. 工作负载：写者、起点、事件与探针

### 2.1 写者

**[已商定]** 一个写者是一个独立的 pi session 序列，带着一个固定的意图任务：读论文、抽取、比较，并写下产物。写者之间：

- 没有共同的计划，也不互相通信；
- 唯一的联系是共享库，彼此写下的内容通过它被看见；
- 读的论文有重叠，重叠程度由语料分配控制（§4.2）。

**写者任务由 I1–I6 生成。** 不同意图的写者会以不同的粒度和关注点写到同一批对象上，这正是 C1、C3 压力的来源。因此，写者数 $K$ 操作化为意图任务的多样性，而不只是 session 的数量。各意图的典型写入见 [Intent 分解](./intents_decompose.md) §7.1.1。无论哪种意图，所需论文不在库中时，写者都要先读论文、按论文表单入库；这一步是有据层写入与 C1 压力的主要来源。

**写者轮流执行。** 同一时刻只有一个写者在提交，事务级并发因此不在贡献范围内（另见 §10 中提交锁外查重的问题）。要测的退化来自语义层面：不同写者对同一对象、同一结论各写一份，而不是并发写入的竞争。

**两条写入路径：**

| 路径 | 含义 | 对应设计 |
| --- | --- | --- |
| 直接写共享库 | 写者经 `Commit` 和 Agent 算子写入全局库 | [提交契约](./commit_contract.md) |
| 项目回流 | 写者从全局库 Fork 出项目库，在项目内工作，再经 Merge 推回 | [项目视图](./project_views.md) §5–§6 |

T1 第一阶段是否只走直写路径，取决于“不变式 × 合并”骨架是否采用（§9）。

### 2.2 起点

**[已商定]**

- 起点只有论文原文（固定版本的 `Material`）与外部标识。有据层与解释层都由写者构建，不预设权威快照。
- 可选的引导，即身份锚点（任务、主数据集、度量）与种子论文，在各组之间完全相同。A0 以文件形式拿到同样的内容。
- 种子不能与金标准重合，探针也要避开种子论文。
- Wikidata、OpenAlex 等只作为标识命名空间，不作为起点快照。
- 读侧的受控对比使用 T1 检查点上的快照（§5）。

“空起点还是引导起点”是否作为一个因子，待定。

### 2.3 注入事件

时间线上预先写定若干事件。事件对写者不可见，在指定的检查点发生。C4 的评测也在这里完成。

| 事件 | 做法 | 检查什么 | 所在层 |
| --- | --- | --- | --- |
| 读错后修订 | 某写者的一条记录含一个错误数值，之后由另一写者对照原文锚点修订 | 修订是否附锚点与理由；依赖它的产物是否被标为过时；旧值能否读回 | 有据层 |
| 撤回 | 撤回一篇论文或一条记录（删除变更集或 `revert`）；解释层写一条 `OPPOSES` | 影响范围查询的正确率与误报 | 两层 |
| 材料变更 | 固定一份源材料的新版本，例如 arXiv v2 改了数值 | 产物的可能过时提示；不预设自动语义重评 | 两层 |
| 写者分歧 | 两个写者对同一对象写出不同内容 | 有据层：是否被检出，并回到锚点修订；解释层：是否并存、各带来源、读者是否看得到 | 两层 |
| 分支与回流 | 两条研究线路从同一基线 Fork，各自前进，再推回全局库 | 项目隔离、上下文闭合、推回时的查重与冲突、历史可见性 | 依赖 Fork / Merge |
| 回看 | 查询某份早期产物在形成时依据的知识状态 | 历史读取的正确性；区分产物的输入谱系与知识状态的提交祖先 | — |

分歧与修订事件优先取材于真实历史，例如复现不一致、arXiv 版本差异、勘误，以及银标准与原文不一致的条目（§7.2）；不够时再人工构造。

[项目视图](./project_views.md) §8 的不变式（视图选择闭合、上下文完整、提交记录完整、项目隔离），在这些事件发生后逐项核对，计入 L0 与 L3。

各对照组经历同样的事件。A0 可以用 git 历史和自己维护的笔记应对，我们比较的是应对的正确率和代价。

### 2.4 读者探针

**[已商定]** 探针按 I1–I6 的任务形式设计，有公开任务作为依据，不是为本系统量身定制的。探针由一个固定的读者 Agent 执行。读者与写者分开，从而把“库的质量”与“读者的能力”分开衡量。

为了测到退化，探针要落在多写者交汇处（[Intent 分解](./intents_decompose.md) §7.1.2）：

- 被两个以上写者、在不同意图下写过的对象；
- 经历过修订、撤回或写者分歧的有据层记录；
- 输入已被修订的产物；
- 所需内容由另一意图的写者写下的问题（C5）。

**[已商定，来自先导决定]** 另有一批**银标准探针**，从写入段论文的 PwC 条目中抽取，按论文分层。四组回答同一批探针；回答与 PwC 不一致时，回到原文锚点裁决（§7.2）。数值不存在图中，所以这批探针测的是“找到并读对”。

**[提议]** 每个探针在冻结时标注以下属性，用于报告时分组：

- 意图（I1–I6）与访问负载（Q1–Q6）；
- 所在层（有据 / 解释）；
- 交汇类型（以上四类之一，或无交汇）；
- 是否依赖注入事件。

无交汇的探针作为对照：A3 在这类探针上不应有优势，有优势反而说明收益来自别处。

## 3. 对照组与消融

### 3.1 对照组

| 组 | 配置 | 回答的问题 |
| --- | --- | --- |
| **A0 文件加 git** | 共享一个 git 仓库，Agent 用 markdown 自由组织（可参照 llm-wiki 一类做法），允许自建索引、目录约定和 AGENTS.md；与 A3 共用文件层 | 最强的反驳：通用 Agent 自己能否维持共享积累的质量 |
| **A1 RAG** | 论文原文与写者产出的笔记、产物一起进入同一个向量索引，读者检索；给它与 A3 同等的预计算预算 | 无结构的积累，在预计算预算相同的情况下 |
| **A2 同一 schema 的裸图库** | 同一 schema 放在裸 Neo4j 上，写者与读者用 Cypher，不经身份查重、契约检查与谱系记录 | 通用后端加合适的查询是否就够了 |
| **A3 完整系统** | PaperWeave 默认配置 | — |
| **A4 agent memory** | **[提议]** 同一个 pi 经 MCP 接入现成的 agent memory 系统，候选是 Mem0 与 Zep / Graphiti，二者都有 MCP 接入，需核实 | 摘要的对照对象：单主体记忆的“最新写入即真值”语义，在共享场景下是否退化 |

**[已商定]** 必须给 A0 最强配置，不能默认文件系统组每轮失忆。如果 A0 只在弱配置下输，T1 就没有说服力。A0 与 A3 共用文件层，二者之差正好是图层上的机制。A2 与 A3 共用 schema，二者之差只来自机制；与 A0、A1、A4 的比较混有 schema 的作用，需如实标出。

**A4 的公平性（提议）：**

- 记忆系统内部抽取与更新所用的 LLM，与 pi 用同一个模型；
- 它的内部 LLM 调用计入成本账本；
- 它按自己的语义（例如 Mem0 的 ADD / UPDATE / DELETE）裁决冲突，这正是要对照的行为，不做改动；
- 对它的配置只做文档推荐的设置，不为本负载调参。

I3 的三组设置 S、S-Cypher、R0（`experiments/e09/i3/`）是 A3、A2、A0 的原型，扩展成 T1 的配置。

### 3.2 消融

**[提议]** 每项消融拿掉一个经典机制，在 A3 上进行。具体去掉什么，需要与代码对应后确认：

| 消融 | 去掉什么 | 预期暴露的退化 |
| --- | --- | --- |
| **−身份** | Commit 不给出候选、不要求 `confirm`；每次新建都生成新节点。可加一档“只保留精确键” | 重复率上升 |
| **−契约** | 不校验引用与必填字段，接受无法解析的引用 | 悬空引用率上升，产物不可复查 |
| **−谱系** | 产物不记 `USED`、`Material` 哈希与输入，`_stale` 无从计算 | 过时识别率下降 |
| **−版本** | 原地覆盖：有据层修订不留旧值与理由，Log / Show / Diff / AsOf 不可用 | 冲突被静默覆盖，回看失败 |

另有一项读侧消融放在 §5：用 Cypher 代替访问算子，即 A3 的写侧加 A2 的读侧。

## 4. T1 主实验：多写者积累时间线

### 4.1 语料：先导，然后正式运行

**[已商定，见 [T1 先导语料](../../decisions/2026-10-10-t1-pilot-corpus.md)]** 先导选了三个领域：

- 时序预测（主榜单 ETTh1）、节点分类（Chameleon），这两个重叠高；
- 关系抽取（DocRED），重叠低，作对照。

每个领域按固定规则抽 10 篇：最早 2 篇作种子论文，其余 8 篇交给 pi 写入。

先导的用途：

- 跑通全流程，即“种子 → 多个带不同意图的写者 → 探针”；
- **直接在库中测量真实的写入重叠**，这是 T1 的前提；
- 估计每篇论文的写入成本，用来定正式规模。

先导结果不进入最终结论。

**正式运行：**

- 领域与规模在先导测得写入重叠之后再定；
- 主要的重叠控制，在同一领域内通过论文分配来实现；
- 跨领域的对比只作辅助证据，即剂量-反应；
- 语料按发表时间排序，写者按时间顺序接触论文，这样 L4 的时间切分（§6）可以复用同一份语料。

### 4.2 变量

| 变量 | 候选取值 | 作用 |
| --- | --- | --- |
| 写者数 $K$ | 1、2、4、6；$K$ 增大时意图种类随之增加 | 主自变量；$K=1$ 是单 Agent 的边界条件 |
| 论文重叠 | 低 / 中 / 高，由分配给各写者的论文集合的交集控制 | 控制不同写者撞上同一对象的频率 |
| 写入量 | 按检查点累计，例如每接触固定数量的论文 | 横轴 |
| 事件密度 | 每个检查点注入的事件数 | 视预算而定，可以固定 |

**[提议]** $K$ 与意图多样性绑定，带来一个混淆：$K$ 的效应里混有意图组合的效应。缓解办法有两个：

- 对同一个 $K$，至少跑两种意图组合，报告方差；
- 加一组同意图、多 session 的对照，即 $K$ 个写者都做同一种意图，用来分离“意图不同”与“人数多”两种效应。

### 4.3 度量

在每个检查点上测量，画成随写入量变化的曲线，并按 $K$ 和组别分组。

**下游正确率（跨组可比的主指标，[已商定 2026-10-11]）：** 在每个检查点上，用 §2.4 的探针跑一遍。

- 有据层探针以原文锚点为金标准，例如集合的精确率与召回率、数值是否读对；
- 解释层探针见下文。

探针正确率衡量的是整条链路：写者写入，库存放，读者找到，读者读对。它不只反映库。各组之间相同的因素有读者的能力和模型记得的知识；不同的因素是绕开库读原文的倾向。库对写者的反作用，例如 dry_run 的候选与阻塞项改变了写者写什么，是要测的效应，不算混淆。所以主指标必须和下面两项配合报告，单凭它不能说明“库更好”。

**参照线：**

- **闭卷下限：** 不给库，也不给论文，读者只凭模型作答。闭卷能答对的探针，或者剔除，或者单独报告；
- **神谕上限：** 直接把金标准中的记录与锚点交给读者。在上限条件下仍然答错，问题在读者，不在库。

各组的分数放在下限与上限之间解读。读者太弱时各组都错，太强时各组都对，组间差距都会被压缩，参照线能把这种情况暴露出来。

**逐题归因：** 每个答错的探针，依据读者的工具调用轨迹，并回到库中逐条检查，归入下列一类：

| 类 | 判定 | 归属 |
| --- | --- | --- |
| 1. 库里没有，或存错了 | 金标准内容在库中缺失、重复、误合并、值错，或被静默覆盖 | 写侧（C1–C3） |
| 2. 库里有，但没找到 | 内容正确地在库中，读者的调用轨迹没有读到它 | 读侧（C5） |
| 3. 找到了，但读错或用错 | 读到了正确的内容，回答仍然错 | 读者，不计入库 |
| 4. 绕开库读原文才答对 | 答对，但依据来自直接读取源材料 | 不计作库的收益（§8.2） |

各组的差异应主要落在第 1、2 类。如果 A3 的优势主要来自第 3 类减少，说明收益来自读侧接口让读者读得更顺，而不是积累的质量，结论要相应改写。第 2、3 类还可以在 §5.1 的读侧受控对比中，在固定的库上单独比较。

**库健康度（诊断，不需要 judge）：**

| 指标 | 定义 | 金标准 | 可测的组 |
| --- | --- | --- | --- |
| 重复实体率 | 同一现实对象在库中对应多个实体的比例 | 实体对齐的抽样标注；数据集与指标可借 PwC 做部分对齐 | A2、A3、消融；A4 的 Graphiti 部分可测；A0 抽样标注 |
| 误合并率 | 不同对象被合成一个实体的比例 | 同上，与重复率一起报告，避免只压低重复率 | 同上 |
| 悬空引用率 | 引用指向不存在、已被改动或无法解析的对象的比例 | 确定性检查 | A2、A3、消融；A0 检查文件链接 |
| 有据层忠实度 | `stated_by: paper` 的记录与原文锚点一致的比例 | 强模型对照锚点核查，加人工抽检 | 有显式记录的组 |
| 冲突检出率 | 有据层的分歧中，被检出并回到锚点修订的比例 | 注入事件，按构造给出 | 全部组（经探针） |
| 静默覆盖数 | 先写的值被后写的覆盖、且没有留下痕迹的次数 | 由变更日志或 git 历史确定 | A2、A3、A4、A0 |
| 过时识别率与误报率 | 修订、撤回或材料变更后，依赖它的产物被正确标为需要复检的比例；误报一并报告 | 由依赖关系确定 | 全部组（经探针） |

**解释层（不测真值）：**

- **分歧保留率：** 两个写者的不同判断，在库中是否都还在，并且各带来源；
- **分歧可见率：** 探针触及有分歧的对象时，读者的回答是否提到了分歧。

**C5 可发现性（提议）：**

- **找到率：** 对“所需内容由另一意图写下”的探针，读者在作答过程中是否读到了金标准中的记录或产物。这一项从读者的工具调用轨迹统计，A0 中读到对应文件即算找到；
- **找到后的正确率：** 把“找不到”与“找到了但读错”分开；
- 与同意图写者写下的探针对比，差值就是跨意图的代价。

**观测量（不作为主张）：**

- 使用次数与正确性是否相关，即是否出现错误级联；
- schema 覆盖不足：写入内容装不进类型的次数，以及最后的去向（Artifact 文档、描述字段或被丢弃）；
- 绕过率：直接读源材料、绕开 PaperWeave 的比例（§8.2）。

### 4.4 结论形式与统计

- **[已商定]** 比较各组的退化斜率随 $K$ 的变化。如果 A3 的斜率不显著优于 A0，T1 不成立。
- **[提议]** 统计单位是独立的时间线，不把同一时间线上的多次查询当作独立样本。斜率用混合效应回归估计：指标作为检查点与组别的函数，时间线作为随机效应。置信区间用按时间线聚类的 bootstrap。每种配置的重复次数，在先导测出方差之后再定。

审稿人可能会问：加了约束更好，这不是理所当然吗？真正有信息量的是两件事：

- 文件加 git 在什么规模、什么重叠下开始输；
- 输掉的部分具体来自哪种退化。

因此，曲线的拐点和消融归因比最终分数更重要。如果 A0 在我们能负担的规模内始终不输，这本身就是值得报告的结果，主张要相应收窄。

## 5. 读侧受控对比与能力阶梯 L0–L4

### 5.1 读侧受控对比

**[提议]** 在 T1 某个检查点的 A3 快照上，固定库的内容，只换读侧：

- **访问算子 vs Cypher：** 同一份知识、同一个 Agent、同样的预算，对比 PaperWeave 的访问算子与有充分 schema 说明的 Cypher。这就是 A2 与 A3 的读侧差异（[Intent 分解](./intents_decompose.md) §7.3）；
- **检索面消融：** 词面、向量、融合；节点文本检索、关系硬过滤、关系扩展、完整视图装配；
- **分歧与过时随结果返回 vs 不返回：** 检验“读者不会主动查 provenance”这一条改变。

这部分只回答使用阶段的问题，与 T1 的全流程对比分开报告。

### 5.2 能力阶梯

阶梯的作用是归因：下游效果提升时，能说清提升来自哪一层。它不要求把所有能力都完整测一遍。

| 层 | 能力 | 对应访问负载 | 金标准来源 | judge |
| --- | --- | --- | --- | --- |
| **L0 存储语义** | 身份与引用校验、契约拒绝、谱系可达、版本读取、不变式 | — | 脚本化的写入序列与预期状态；负例测试 | 不需要 |
| **L1 关联检索** | 跨论文按对象和条件查找记录 | Q1–Q4 | 银标准与排行榜类标注（§7），集合的精确率与召回率 | 不需要 |
| **L2 组合** | 跨论文比较表；组合时条件能被正确保留 | Q5–Q6 | ArxivDIGESTables 的参考表；条件与证据抽检 | 部分需要 |
| **L3 有状态工作** | 跨 session 接续工作；修订后的影响范围；读取旧状态 | — | 脚本化，与 §2.3 的注入事件共用 | 基本不需要 |
| **L4 端到端** | 时间切分的实验设计任务（§6） | Q6 | 后来发表的论文实际采用的实验设置 | 需要，并配人工抽检 |

e09 种子上的实例保留为试点用例，挂到对应层上：

- **L1 / L2：ETTh1 跨论文比较。**“在 ETTh1、horizon $T=720$ 时，DLinear 和 PatchTST 各自报告了什么结果？两者的 look-back 设置和切分约定是否一致？”答对需要通过共享节点 `dataset_0002`（ETTh1）连接 S5.T3 与 S4.T3，并对齐 $L=96$、Autoformer 切分约定等条件。
- **L2：条件迁移。**“新数据集上可以用 $L=512$，能直接引用 DLinear 的‘大 look-back 有效’吗？”答对需要 S5.T4 上的条件：DLinear 用 $L=336$，而 FEDformer、Autoformer 保持 $L=96$，比较并不对称；ILI 行的 horizon 标签疑为误印。
- **L1：宣称与核验。**“DLinear 在 Weather 上胜过 FEDformer 的数值，是 DLinear 作者自己跑的吗？”答案是否定的：FEDformer 等六行数值取自 FEDformer 论文，依据在原文第 172 行。这一例检验 EVALUATES 边上的 own / rerun / cited / unstated 四级来源能否被正确使用。
- **L0：身份判例。** e09 论文文档开头的 `confirm` 块提供试点参考答案，例如 `$dlinear` 不同于 `method_0008/0007/0002/0004/0010`。

**责任边界：** 语义判断在 Agent 一侧。L0 和 L1 测的是模型与契约能否表达、校验和找到这些判断，不宣称 PaperWeave 自动做实体链接或推断矛盾。

## 6. L4 下游任务：时间切分的实验设计

PaperBench 不合适：它主要测写代码和复现结果的能力，知识库的作用很小，而且和编码能力混在一起。

**任务：**

1. 用时间点 $t_0$ 之前的论文建库。T1 时间线结束时的库可以直接使用，各组用各自积累出的库。
2. 取 $t_0$ 之后发表的目标论文，只给 Agent 它的研究问题和方法描述。
3. 要求 Agent 给出实验设计：应对比哪些 baseline，用哪些数据集和指标，已有结论在什么条件下成立。
4. 金标准是目标论文实际采用的实验设置，不需要我们另行标注。

**度量：** baseline、数据集、指标各自作为集合，计算精确率与召回率；条件说明由 judge 评分并人工抽检；同时报告成本。

**这个任务能回应的质疑：**

- **缺乏对比：** 金标准来自外部，所有组在同一语料上运行。
- **收益来源：** 几百篇论文不可能在一次任务中逐篇读完，测到的收益只能来自关联与复用。
- **数据泄露：** 目标论文选在被测模型的知识截止日期之后。

**已知局限：**

- 目标论文的实际选择不一定最优，只是一个合理的参照。金标准只用于计算集合重合度，不把“与目标论文一致”说成“正确的科研决策”。
- 写者是否会写入与目标论文高度相关的内容，取决于语料与写者任务。冻结任务前需要检查泄漏。
- 关系抽取领域在 PwC 上 2023 年后基本断档，时间切分在这个领域很弱。L4 以时序预测或节点分类为主。

## 7. 金标准

### 7.1 按层定义

**[已商定]**

- **有据层：** 对照原文锚点。对错指是否忠实于原文，不是科学真理。
- **解释层：** 不测真值，只测分歧是否被保留、读者是否看得到。
- **身份：** 实体对齐抽样标注；外部标识（arXiv ID、DOI、仓库 URL）给出部分真值。

**核查者：** 种子核实与银标准裁决由强模型对照锚点完成，再用人工抽检校准一致性（如 Cohen's $\kappa$）。核查模型与 pi 的写入模型不同源（候选是 gpt6-astra）。人工抽检的比例事先固定。

### 7.2 PwC 银标准

**[已商定，见先导决定 §3、§6]**

- PwC 快照已经固定，是外部、事先就存在的参照，可以避免“自己出题自己判”的质疑。
- 它是银标准，不是金标准：条目由社区录入或自动抽取，会有错误和缺失。
- 与 PwC 不一致时，回到原文锚点裁决，结果分三类：我们对而 PwC 错；PwC 对而我们错；两者都说得通，例如一方用自报数字、一方用重跑数字。
- 这些不一致本身可以作为分歧与修订事件的真实取材（§2.3）。
- 写者不能看到 PwC：pi 有 shell 和网络，可能查到归档，模型也可能记得榜单数字。是否断网待定；在此之前，审计这类访问。

### 7.3 公开数据的用途

目前没有现成的 benchmark 能同时覆盖论文知识、Agent 产物、多写者持续写入、项目视图与版本历史。外部数据用来提供真实性与独立性；状态与操作序列由我们另行定义。

| 来源 | 可用的部分 | 不足与使用方式 |
| --- | --- | --- |
| Papers with Code 归档 | 任务、数据集、结果榜单 | 先导的候选池与银标准（§7.2）；覆盖面小，录入不完整 |
| TDMS（Hou et al. 2019）、AxCell、SciREX | 任务、数据集、指标、结果的标注 | L1 探针与实体对齐的参照；领域覆盖与可获取性待核查 |
| LEGOBench（`2024-LEGOBench`） | 基于 arXiv 与 PwC 的排行榜生成任务 | L1 抽样；需确认归档数据是否完整 |
| SciLead（`2024-SciLead`） | 人工整理的 TDMR 排行榜 | 比社区数据更可靠的 L1 参照；规模较小 |
| [AstaBench：ArxivDIGESTables-Clean](https://github.com/allenai/asta-bench/blob/main/README.md#available-tasks) | 跨论文结构化比较表及参考产物 | L2 金标准；原协议不测跨 session 与版本，改造后作为新负载报告，不沿用官方分数 |
| [AstaBench：ScholarQABench2、PaperFindingBench](https://github.com/allenai/asta-bench/blob/main/README.md#available-tasks) | 文献问答与检索任务 | I1、I4 探针的任务形式；分数混合了检索与推理，不当作存储层正确性指标 |
| QASPER、SciFact | 全文证据问答；支持或反驳证据 | I2、I5 探针的任务形式；SciFact 的内容属于生物医学，只借形式 |
| MemoryAgentBench（`2026-MemoryAgentBench`）、[LongMemEval](https://github.com/xiaowu0162/LongMemEval) | 增量积累、知识更新、选择性遗忘 | 借鉴 L3 的任务形式与 A4 的配置方式；对象是单主体记忆，不作为主分数 |
| ResearchBench（`2026-ResearchBench`） | 从论文抽取研究问题、背景与假设 | 可借鉴 L4 目标论文输入的构造 |
| [OpenAlex 数据快照](https://help.openalex.org/access/snapshot/) | 大规模论文元数据 | 身份锚点引导；规模压力测试（§8.3）与 T2 的粗略估算；不提供语义金标准 |
| [LDBC SNB](https://ldbcouncil.org/ldbc_snb_docs/) | 读写混合负载与规模档位的设计方法 | 只借鉴方法 |

**筛选规则：**

- 先从外部数据中筛出材料可获取、目标可独立核验的实例，冻结筛选规则后再确定测试集；
- 开发种子与正式测试按领域或任务簇划分，不按单个问题随机划分；
- 报告选入与排除的数量及原因。

## 8. T2 成本账本、可用性与系统开销

### 8.1 成本账本

成本分项记账。在 T1 时间线的每个检查点，同时报告增量和累计值；失败的调用和对原文的直接读取都要计入：

- **构建：** 抽取与入库的 token 和时间，dry_run 来回轮数（`IngestBatch` 已有统计）；
- **写回：** 产物写入与契约校验的额外开销；
- **使用：** 每次下游任务的成本；
- **维护：** 修订、撤回、材料变更之后的复检开销；
- **A4 的内部调用：** 记忆系统内部 LLM 的调用。

盈亏平衡点：

$$
N^* = \frac{C_{\text{build}}}{c_{\text{base}} - c_{\text{ours}}}
$$

其中 $C_{\text{build}}$ 是构建与维护的总成本，$c_{\text{base}}$ 与 $c_{\text{ours}}$ 分别是对照组和 A3 每次使用的成本。

成本有三种合理的表述：

1. **写回开销。** 知识积累是 Agent 正常工作的副产品，它本来就要读论文。我们报告的是比“只读不写”多花了多少，而不是整个库的构建费用。这是最诚实的表述。
2. **摊销。** 共享库由许多使用者分摊，$N^*$ 随使用者数增加而更容易达到。**前提是对照组拿到同等的预计算预算**，否则差异可能只来自“我们做了预计算而对照组没做”。
3. **离线与在线用不同模型。** 构建阶段用便宜模型，使用阶段用强模型，与 T3 呼应。

平台级成本（用 OpenAlex 年度快照或一年的会议论文总量估算）只放在讨论部分，作为粗略估算。

### 8.2 Agent 是否用得顺手

这些指标必须和正确率一起报告，因为用得顺手不等于结果正确：

- **交互效率：** 工具调用次数、无效调用率、dry_run 来回轮数、被拒写入后的恢复率（拒绝之后，Agent 能否按阻塞项修好再提交）；
- **显示偏好：** Agent 保留了文件与 shell 权限，我们只审计、不禁止它绕过 PaperWeave。它多常绕开、直接读原文，本身就是“好不好用”的证据。绕过所得的答案不计作复用；
- **模型强度扫描：** 即 T3。

### 8.3 系统开销与可扩展性

**[提议]** 这是 SIGMOD 审稿人一定会问的部分，旧版草案没有。测量对象是存储层本身，不经过 Agent：

| 测什么 | 自变量 | 对照 |
| --- | --- | --- |
| Commit 延迟，含 dry_run 查重 | 库中对象数、单批大小 | A2 直接写 Cypher |
| 访问算子延迟（Search、Traverse、ReadEvidence） | 库中对象数、遍历扇出 | A2 的等价 Cypher |
| `_stale` 读取时计算的开销 | 依赖链深度与扇出、产物形成之后的提交数 | 不返回过时提示 |
| AsOf / Diff 延迟 | 历史长度（提交数） | — |
| 存储增长 | 提交数；graph-vc 变更集相对当前状态的体积 | 无版本的库 |

规模的来源分两部分：

- 真实的语义实例来自 T1 时间线，负责正确性；
- 扩展到更大规模时，用 OpenAlex 元数据批量导入身份锚点，再重放或复制 T1 的写入序列。生成的数据只用于压力测试，并单独标注。

**规模的三个维度**（沿用旧版）：

- **语料规模：** 论文数、对象数、依赖边数，决定系统的规模；
- **写者与历史：** 写者数 $K$、每条时间线的提交数、注入事件数，决定积累效果。只增加论文数，证明不了积累的收益；
- **任务广度：** 独立时间线和领域的数量，决定结论能外推多远。

## 9. “不变式 × 合并”骨架（提议，待确认）

标题 *Collaborating without Coordinating* 会让审稿人期待 I-confluence、CALM 那样的分析：哪些不变式不需要协调就能维持。提议按“两个各自合法的状态合并后是否仍然合法”给库的不变式分类：

| 不变式 | 合并两个各自合法的状态时 | 维护方式 | T1 中的检查 |
| --- | --- | --- | --- |
| 来源与谱系完整（只追加） | 并集仍合法，可以直接汇合 | 无需介入 | 悬空引用率；谱系可达 |
| 解释层判断并存 | 并集仍合法，分歧本身就是数据 | 无需介入 | 分歧保留率与可见率 |
| 实体身份唯一、引用完整 | 可能违反，例如两边各建了一个 PatchTST | 存储层在提交与合并时调停（查重、确认） | 重复率与误合并率 |
| 有据层单值 | 可能违反，例如两边对同一结果读法不同 | 回到原文锚点修订，保留历史 | 冲突检出率；修订正确性 |
| 派生产物新鲜 | 输入变化后，产物可能过时 | 依赖追踪：只标记，不重算 | 过时识别率与误报率 |

采用这个骨架，对评测有三个影响：

- T1 的度量按这五行分组报告，消融也对应这几行，直接回答“写入者之间不协调，由存储层居中调停”这句话；
- “合并”在直写路径上，就是一次提交与当前库状态的合并；在项目路径上，就是 Merge 推回。前者第一阶段就能测；后者需要 Fork / Merge 实现之后才能测，这样 Fork / Merge 就不能再推迟到第二阶段；
- 各行的结论按定义看大体成立，但还没有形式化。形式化做到一个命题加逐条论证即可，不需要一套完整的理论。

待定：是否采用这个骨架；Fork / Merge 是否提前到第一阶段。

## 12. 风险与可能的负结果

- **写入重叠不足。** 先导中如果写者很少撞上同一对象，T1 测不出退化。应对：先改论文分配，提高同一领域内的交集；仍然不足，就如实报告并重新考虑领域。不能为了制造重叠而人为指定写者写什么。
- **A0 不输。** 在可负担的规模内，文件加 git 的退化斜率与完整系统相当。这时报告文件加 git 足够的区间，把主张收窄到更大规模或更高重叠的场景，不换成对我们有利的负载。
- **A4 配置被质疑。** 记忆系统不是为这个负载设计的，审稿人可能说对照组不公平。应对：只用文档推荐的配置；同时说明这正是要检验的前提差异，即单主体与共享。
- **约束的代价超过收益。** 契约校验与拒绝导致写回成本过高，Agent 频繁绕开 PaperWeave。显示偏好与恢复率会直接暴露这一点。
- **退化只来自某一项约束。** 如果消融显示只有身份查重有效，主张相应收缩。这本身也是有价值的发现。
- **$K$ 与意图组合相混。** 见 §4.2 的缓解办法。
- **泄漏。** 写者查到 PwC 归档；模型记得榜单数字；种子与金标准重合；L4 的目标论文内容已被写入库中。逐项审计。
- **judge 偏差。** judge 与写者、读者的骨干模型不同源；用多个骨干复跑，报告方差与显著性；人工抽检比例事先固定。这是吸取 AgenticScholar 用同源裁判、不报告方差的教训。
