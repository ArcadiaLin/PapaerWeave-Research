## 1 要回答的问题

评测要回答一个问题：

> 许多互不协调的写者往同一个库里积累论文衍生的知识；后来的读者不在写入现场，手里也没有原文，只有这个库。他们能否答得和“所有原文都摆在手边”一样好？写者越来越多时，库能否保持这一点？

这个问题有两个来由。

- **常见的记忆评测测不到它。** Mem0、A-MEM、Zep 在 LoCoMo、LongMemEval 上的评测，写入靠系统自己的摄入管线，读取是“检索 top-k 加一次回答”，读者没有自主性。我们的写者和读者都是通用 agent，中间件不做内部 LLM 推理，所以每次读写都是一次完整的 agent 运行。
- **最强的反驳是文件。** Letta 报告过，gpt-4o-mini 的 agent 只用文件与 grep，在 LoCoMo 上达到 74.0%，高于 Mem0 自报的 68.5%。f1 的 10 道抽查也是如此：两组都答完的题里，单篇取值、条件、代码这几类，A0 与 A3 都拿满分。所以“读者 + 原文”和“读者 + 文件库”是必须正面比较的强参照，不能回避。

## 2 各组提供什么

### 2.1 写者组

四组跑同一张任务表（10 个写者身份、70 个会话、30 篇长期预测论文、同一份种子），只有库和写入接口不同。

| 组 | 写者接触库的方式 | 写者另有 | 与 A3 之差隔离出的东西 |
| --- | --- | --- | --- |
| **A3 完整系统** | PaperWeave 的 MCP 服务 | 论文与固定 commit 的代码（只读） | — |
| **A2 机制全关** | 同一服务，关掉查重、修订约束、过时标记、受影响产物四项 | 同上 | 只有机制 |
| **A0 文件 + Git** | 共享 git 仓库；约定文档与模板由 A3 的工具说明翻译而来，文字对等，没有任何执行 | 同上 | 机制、图层与读取接口合在一起 |
| **A4 Graphiti** | Graphiti 的 MCP 服务 | 同上 | 与一个 agent 记忆系统的差别 |

- 〔已确认 2026-10-17〕A0 与 A3 文字对等、机制不同。打磨 A0 时只修指令失败（没看懂约定、格式写错），不修机制失败（漏掉重复、没发现过期、改了别人的内容不留理由、格式漂移、引用失效），不给 A0 脚本。
- 〔已确认 2026-10-17〕保留 A2，A2 与 A3 共用代码；A3 的改进除四项被关的机制外，A2 自动获得（D34）。
- 〔已确认 2026-10-19〕不发 skill（D25）；会话开始时的库总览是 A3、A2 共有的接口，不单独做消融（D26）。

### 2.2 读者条件

读者每题一次会话，彼此之间没有记忆，提示语只有 `{TOOLS}` 一处按组替换。

| 条件 | 读者拿到 | 不给 | 作用 |
| --- | --- | --- | --- |
| **各写者组（A3、A2、A0、A4）** | 该组检查点快照上的只读库，外加按锚点读原文 | 浏览或检索原文全文；代码 | 被检验的组 |
| **P 原文组** | 检查点上已入库的全部论文（同一版本），用 pi 自带的文件工具 | 任何库 | 阳性对照：现实中做得到的最好情况。相当于 A0 不写笔记、直接 grep 原文作答 |
| **C 闭卷组** | 只有题目 | 库与原文 | 阴性对照：这道题是否非要原文不可 |
| **D 段落组** | 只有这道题依据所在的原文段落，放在提示语中 | 库、其余原文、工具 | 读者能力的上限：材料给对了仍答错，问题出在读者或判分 |

〔已确认 2026-10-21〕**原文属于库。** 论文以 `Material` 的身份按内容哈希登记入库，锚点是库中的正式引用；读者必须能读到锚点指向的内容，包括论文原文。f1 中的读者条件（`store_only`：`read_evidence` 只读产物文档）切断了这一步，A3 因此被自己“不转录锚点能给出的内容”这一原则拖累。k30 的 200 个会话中，A3 有 86 个、A2 有 87 个读者顺着锚点去读原文而被拒；抽查中 A3 的那道 T8 记 0 分，原因也在这里。

〔提议〕**只能经库读原文，不能浏览。** 读者能读的范围是检查点快照中记录过的锚点，以及它们的子区间。记录过的锚点指出现在任何节点、边或产物文档中的 `<id>::<起>:<止>`。

- A3、A2：`read_evidence` 增加“只读已记录锚点”的模式，替换现在的“只读产物文档”。
- A0、A4：提供规则相同的只读命令，从检查点快照中机械地收集锚点；论文目录不挂载。A0 的文件里用的是同一种锚点写法，能否完整收集要先核实；A4 只有写者写进 episode 的锚点才算。
- 锚点之外能否放宽几行上下文〔待定〕。

这条规则对应我们要的场景：读者没有现成的原文，库把他带到哪里，他就读到哪里。读者自己通读论文得来的收益不算库的（V2 草案 §1.4）。

〔已确认 2026-10-21〕**D 段落组的材料取自题库。** 每题的 `evidence` 与要点的 `anchor` 都是原文锚点，按统一规则取出段落，交给同一模型作答，判分与其他条件相同。不需要库与工具循环，一次调用即可。〔提议〕取段落的规则：

- 表锚点（`<arxiv>:T<行>`）取整张表；落在表内的行锚点扩展为所在的整张表（起止行见题库 `facts/tables.csv`）；正文行锚点扩展为所在段落。
- 依据只指向“出现了什么”的题，要按金标准补齐判断“没有出现”所需的材料。例如 T6 的依据只有源论文的主表，而金标准 `still_reported` 列出的后来论文的主表都要补上。正式运行前按题型逐一核对依据是否充分。
- D 段落组去掉了“找”，只剩“读”，只作上限参照；A3 与 D 的差是“找材料”上丢的分。

〔提议〕**代码题（T16–T18）仍作辅助组**，单独报告。代码锚点进数据模型之前（意图 V3〔待商定〕），读者条件为：库加上该组写者阶段同样的代码目录。

## 3 主张与检验

| 编号 | 主张 | 比较 | 成立的条件 | 证伪 |
| --- | --- | --- | --- | --- |
| **H0 题有效** | 这批题非得读原文才答得出 | P 对 C | P 显著高于 C | P 与 C 相当：题靠模型记忆就能答，后面的非劣效没有意义；闭卷能答对的题剔除或单列 |
| **H1 替代（主结果）** | 共享库可以替代手边的全部原文 | A3 对 P | 差的置信下界高于 $-\delta$，且成本不高于 P | 下界低于 $-\delta$ |
| **H2 多写者完整性（E1）** | 写者增多时，A3 的库保持住，文件库保持不住 | A3 对 A0：库层指标随检查点的变化；各组与 P 的差距随检查点的变化 | A0 的 M6、M5 变差，或与 P 的差距扩大；A3 不变差、与 P 的差距不扩大 | 两组在库层指标与差距变化上都没有显著差别：在这个规模上文件够用，如实报告并收窄主张 |
| **H3 机制有用** | 差别来自机制，而不只是图与接口 | A3 对 A2 | A3 在对应指标上好于 A2 | 两者相当：差别来自图层与读取接口，主张改写 |
| **H4 不逊于 agent 记忆（E3）** | 作为记忆不吃亏 | A3 对 A4 | 非劣效，同时报告成本账本 | 下界低于 $-\delta$ |

- P 原文组相当于 A0 不写笔记、直接 grep 原文作答，所以“不写笔记会不会更好”由 H1 直接回答，不另做笔记层的消融。〔已确认 2026-10-21〕不设“库 + 全部原文”的读者条件：它不是目标场景，读者可能完全不看库，结果无法归因。
- 〔用户提出 2026-10-21〕H1 是主结果：在没有原文的条件下，与“全部原文在手”非劣效，是这个设定下最有力的证据。在 30 篇的规模上，P 接近理想情况；论文越多，P 自己越难做好，所以在这个规模上得到的非劣效偏保守。
- H1 主要回答 V2 草案中的 E2（充分性），比 $\rho_I$ 更强：比较对象是现实中能做到的最好读者，不只是同一库的另一种读法。H2 才是 E1 的核心论点；两者合在一张图里报告（§6）。
- **单写者对照的缺口。** V2 的主估计量 $\Delta_{\text{arm}} = Y_{\text{arm}}(\text{多写者}) - Y_{\text{arm}}(\text{单写者})$ 需要一条单写者时间线，V3 没有跑。H2 暂用检查点上的变化代替：写者与写入量一同增长，二者分不开。是否补一条单写者时间线〔待定〕。

## 4 现象与解释

| 观察到的现象 | 说明什么 | 先排除什么 |
| --- | --- | --- |
| P ≫ C | 题需要原文，H1 可以检验 | 判分过松（看 C 的部分分来自哪里） |
| A3 与 P 的差在 $\delta$ 之内，且调用、token、用时不多于 P | 库替代了原文：库知道去哪里看、记下了什么条件 | A3 读者大量读锚点、几乎等于通读：统计每题经锚点读到的行数 |
| A3 明显低于 P | 按逐题归因（§5.3）看缺口在写侧、读侧还是读者 | 失控的题（§5.1）；成本是否远高于 P |
| A0 在单篇取值题上与 A3 相当 | 只要库里有，文件就能找到（与 Letta 的结论一致）；如实报告“这类题文件够用” | — |
| A0 的差距随检查点扩大，A3 不扩大 | 多写者代价，H2 成立 | 负载造成的超时（§7 第 1 条消除）；A0 读者联网 |
| 库里某值存错，而读者答对 | 读者顺着锚点核对了原文：锚点起了保护作用 | 读者是否本来就没有用到那个值 |
| 库里某值存错，读者也答错 | “答错却看不出错”，核心假设的直接实例 | 金标准本身有误：回到原文锚点 |
| 用时与调用集中在跨多篇的汇总题，每次调用的未缓存输入很大 | 读取接口缺少聚合，属于成本问题，不是内容问题 | 推理服务负载：看同台会话数与每次调用的耗时 |
| A3 与 A2 的库层指标相近，但写入时 A3 的“确认不同”远多于 A2 | 查重提示被用上了，但这个规模上真实重叠少 | 先核实前提：语料上的写入重叠是否真的多（f1：A3 0 个重复、A2 1 个） |
| A0 写下的改动没有提交 | 写了却没进入共享库，是文件库特有的知识流失 | 后来的会话是否补上了提交 |
| 读者绕开库：联网，或读到锚点之外 | 库没给够：绕开的比例本身就是好不好用的证据 | 绕开得来的正确答案不计作库的收益 |
| A4 每次调用都带入大段新文本 | 在 agent 记忆一侧，不可缓存的输入是其固有成本 | 负载：看独占推理服务后的数据 |

## 5 度量

### 5.1 读者

- **题分：** 每题 $s \in [0, 1]$，按每题冻结的 `scoring` 计分，判分流程见 §5.4。
- **失控：** 〔已确认 2026-10-21〕读者不设回答时限，只设防失控的安全上限（§7 第 4 条）。触发上限的题记 0 分，单独记为“失控”并逐条列出，不与正常作答混在一起；另报去掉这些题后的敏感性分析。
- **成本：** 每题的调用次数、未缓存输入、缓存读、输出 token、用时。经锚点读到的原文行数单独记一项。不限时之后，成本是 H1 中“代价不高于 P”的直接证据；串行、独占服务（§7 第 1 条）保证用时在组间可比。
- **绕开：** 联网命令、锚点之外的读取（只记录，不阻止）。
- **引用可核对率：** 回答所引的 id 或文件在快照中存在、行号不越界的比例。

### 5.2 库（不经过读者）

在每个检查点快照上测量，确定性优先：

- **M5 转录忠实度：** 库中结果行与原文锚点一致的比例，按错误类型拆开。
- **M6 知识流失：** 记 $C^{ok}_t$ 为检查点 $t$ 上与原文一致的格子，

$$
\mathrm{Loss}(t) = \frac{\lvert C^{ok}_t \setminus C^{ok}_{t+1} \rvert}{\lvert C^{ok}_t \rvert}.
$$

- **M1 重复率**（按对象类型）、**M4 产物碎片化**、**M3 悬空引用**、**未进入共享库的写入**（A0 未提交的改动；A4 正常结束却没写入的会话）、**过时候选**（产物写完后其输入又被改动）。
- 〔已确认，V2 草案 §1.4〕A3 在写入时就执行的检查（悬空、行号越界、引用不存在的 id），只用于 A3 与 A2 的比较，不作为胜过 A0、A4 的证据。

### 5.3 逐题归因

每道没拿满分的题，根据调用轨迹回到快照核对，归入以下一类：

1. 库里没有，或存错了（写侧）；
2. 库里有，但读者没找到（读侧，C5）；
3. 找到了，但读错或用错（读者）；
4. 绕开库才答对（不计作库的收益）；
5. 失控（触发安全上限）。

组间的差异应主要落在第 1、2 类。如果 A3 的优势主要来自第 3 类减少，结论要改写为“读取接口让读者读得更顺”。规模〔待定〕：只做主检查点，或者抽样。

### 5.4 判分

〔已确认 2026-10-21〕由 Claude 子代理对照题库中的参考答案（`gold`）与判分说明（`scoring`）判分。子代理不需要自己找答案，只做对照，是成本最低的调用方式（D31）。

- **一批一道题：** 同一道题在各组（C、D、P、A0、A2、A3、A4）、各检查点、各次运行下的回答，盲化、打乱后放进同一批，与这道题的参考答案和判分说明一起交给一个子代理。参考答案只读一次，尺度一致。约 4000 条回答，约 200 批，每批 10–20 条。
- **盲化：** 去掉组名、模型、路径、工具名，库的标识换成中性记号；映射表不交给判分者（`tmps/probes/grading-plan.md` 第 2、4 节）。
- **主要看 Final answer 段：** 自动题主要对照最终答案段（§7 第 3 条）判分。只在缺少这一段、要判语义子项（T3 的 look-back 说法、T7 的来源类别、T8 是否判定某值正确），或是要点题时才读全文。
- **脚本：** 负责打包与盲化、读回判定、汇总计分；另把 Final answer 中的数值与方法集合同参考答案做一次精确比对。脚本与子代理不一致的条目标出，由我复核。脚本不调用模型。
- **质量控制：** 每题型随机抽 10% 交给另一个子代理独立再判，报告一致率；我复核脚本标出的条目与组间分差最大的题；用户另抽查约 10%。判分者与出题者同属 Claude，论文中写明。
- **先用 D 组校准：** D 组的回答最规整，先用它把盲化、解析与判分提示调好（金标准自洽测试，每题型约 5 条人工核对），再判其他组。
- 判定按（回答、参考答案、判分说明版本）的哈希缓存；判分说明修订后只重判受影响的题。

## 6 统计

- **单位：** 题。主检验用最后一个检查点的主题，每题取各条时间线的均值，对题做 bootstrap。
- **阈值：** 〔已确认 2026-10-19〕$\delta = 8$ 个百分点，单侧 $\alpha = 0.025$。
- 〔提议〕**检验顺序固定**，前一步成立才做下一步，各步都用同一 $\alpha$，整体的第一类错误率不超过 $\alpha$：
  1. H0：$\mu_{\text{P}} - \mu_{\text{C}} > 0$；
  2. H1 非劣效：$\mu_{\text{A3}} - \mu_{\text{P}} > -\delta$；
  3. H1 优效：$\mu_{\text{A3}} - \mu_{\text{P}} > 0$。

  H2–H4 作为次要比较，报效应量与置信区间。
- **分层报告：** 按题型、层级（单篇、两跳、多跳、分歧）与意图分开报告；失控率与成本并列。
- **主图：** 横轴为检查点，纵轴为题分；P 画成参照带，$\pm\delta$ 画成阴影，各组一条线。另一张图为库层指标随检查点的变化。
- 〔提议，拟 D35〕**开发题与保留题：** 按题型分层，把题对半分开。开发题用于诊断与优化 A3；保留题封存，直到定版后的正式运行。f1 的回答只在开发题上判分。2026-10-21 的 10 道抽查题已经看过分数，划入开发题。

## 7 运行协议（f1 的教训）

以下各条对所有组相同，都已确认（2026-10-21），在新一轮冻结时写入冻结记录。

1. 〔已确认 2026-10-21〕**串行推进，每组独占一台推理服务。** 一组运行时独占一台服务，跑完再推进下一组；两台服务可以各跑一组。f1 中 22 次写者超时有 7 次来自同台负载；同台约 4 个其他会话时，每次调用慢 2–5 倍。
   - 两台服务的硬件、sglang 版本与模型权重保持一致，记入 `run.yml`；评测期间不升级、不换权重。两台不一致时，用时不跨服务比较。

## 8 工作负载中的机制场景

### 8.1 产物类型的覆盖

f1 的写者写过排行榜、比较、核查、综述、Note 五类产物（D28）。几个最可能拉开差距的机制落在排行榜以外的类型上：

- **CompareSettings（I3 可比性）：** 引用排行榜中的行，形成产物引用产物的链。排行榜更新后，引用它的比较能否被发现过期：A3 按所引版本判断，并在提交时告诉写者；A0 的文件里只有引用文字。
- **Verify（I5）：** 两个写者在不同证据下核查同一条主张，结论相左。看各组是否保住了两种意见，读者能否答出分歧；丢掉一种计入知识流失。
- **Summarize（I2、I4）：** 没有身份键，两个写者写同一主题会得到两份。看读者能否找到并区分它们，以及所引的实验修订后能否被发现过期。
- **Note（I1、I6，原 Generate，D27）：** 并入读者探针，不单独设计机制场景。
- **Skill：** 不进 E1。

### 8.2 版本变化

f1 只有自然发生的版本更新（3 个会话：FiLM、Is Mamba、Bi-Mamba+ 换新版本）。受控测试〔待定〕：

- **材料：** 选一篇论文伪造一个 v2，变化的位置与内容完全已知，金标准可以自动算出。可另配一篇真实的 v1 → v2 作对照。
- **三种变化与要看的事：**
  - 行号移动：读者能否读对行；维护者能否把锚点改写到新版本。
  - 数值更正：读者能否答出现在的值、是否知道它变过；维护者能否带理由修订，引用它的排行榜能否给出 `superseded` 并被更新。
  - 内容删除：读者能否答出结论是否仍成立；维护者能否删除记录或标为 `OPPOSES`，并留下理由。
- **系统一侧：** `_anchor_version`、产物的 `_stale`（`superseded`、`material`）、材料按内容哈希登记（见[数据模型 V3](./data_model.md)）。
- **指标：** 读者的回答对不对、是否察觉到版本变化、维护后残留的错误锚点与错误数值。

## 9 能证明与不能证明的

**能证明（若检验成立）：**

- 在一个领域、30 篇论文、10 个写者身份的规模上，读者只靠共享库（经锚点读原文）答题，不逊于手边有全部原文的读者，代价不更高。
- 同样的写入负载下，PaperWeave 的库比文件库更能保持住（H2），而且差别来自哪几项机制（H3）。
- 与一个 agent 记忆系统相比不吃亏（H4），并附成本账本。

**不能证明：**

- **更大规模：** 30 篇时 P 很强，论文多了之后才真正需要库，这一点只能讨论，不能声称。
- **其他领域与其他模型：** 只测了长期预测与 qwen3.8-27b。
- **人类使用者：** 读者与写者都是 agent。
- **判分独立性：** 判分者与出题者同属 Claude；靠盲判、确定性计分与人工抽查缓解，不能消除。
- **写者数量与写入量的分离：** 没有单写者对照时，H2 只说明“随积累”，不说明“随写者数”。

**作答**

- 读者：pi 1.2.0，与其他读者同一模型与思考级别，默认的内置工具（read、bash 等）。沙箱与写者组的读者相同，只是 `/work` 下只有 `papers/`。
- 提示语：按 §7 第 3 条，题面原文，加 P 的说明句（含目录说明：论文在 `papers/<带版本号的 arXiv 编号>/paper.md`）与 Final answer 段。
- 并发与其他读者相同；不设时限，安全上限见 §7 第 4 条。先于写者组运行（§7 第 2 条）。
- 次数：P 组与写者无关，每个检查点只需一套回答。〔提议〕跑 2 次，与“每题取两条时间线的均值”对齐。

**输出与审计**

- 写到 `<运行>/answers/P/k<篇数>.jsonl`，字段与其他读者相同（`arm` 记为 `P`）。
- 另记每题打开或检索过的论文与行数（从 read 调用与 shell 命令中统计），用于成本账本：P 没有建库成本，但每个读者都要自己找一遍；库的成本只付一次，由所有读者分摊。

**与现有代码的关系**

- 先导的读者框架（`eval/src/pweval/harness/readers.py`）有 `with_papers` 条件，给的是“库 + 论文”，不是 P 组。P 组要新增一种没有库、只挂载论文的读者条件，并放进正式运行框架（`timeline.py`）的读者阶段。

**怎么读结果**

- P 与 C 的差检验题是否有效（H0）；A3 与 P 的差检验替代（H1）。
- P 在跨多篇的汇总题上用时长、调用多，在单篇题上满分，是预期中的形态：文件够用的地方如实报告，库的价值落在汇总题与成本上。

### 10.3 C 闭卷组

状态：规格已确认（2026-10-21），未实现。闭卷组只给题目，不给库、原文与工具，读者只能凭模型已有的知识作答。它量出“背出来的分”：语料是公开论文，模型训练时可能读过其中一部分。

**输入**

- 题集：`probes/sample.yml` 的 200 道主题；辅助组 6 道代码题（T16–T18）同样作答，另存。闭卷组与库、检查点都无关，金标准也不按检查点重算（D31），所以作答一次，第 10、20 篇检查点取其中的有效子集。
- 不给：库、论文、代码、网络、工具。

**提示语**〔已确认 2026-10-21〕

```text
{question}

No papers, store or tools are available. Answer from what you know.
Where the question refers to "the store" or "the papers in the store", take it to
mean the published papers on this topic that you know of.

{FORMAT}
```

- `{FORMAT}` 是 §7 第 3 条中该题型的 Final answer 段；要点题没有这一段。
- 关于 “store” 的一句只解释冻结题面中的用语（T6、T8 等写着 “the papers in the store”），不透露信息；P、D 各有对应的一句（P：`papers/` 中的论文；D：上面给出的段落）。
- 说明是中性的：不鼓励也不劝阻“不知道”，避免说明本身左右得分。
- 不加第 5 条的环境说明：C 不带工具，用不上。

**运行配置**〔已确认 2026-10-21〕

| 项 | 取值 |
| --- | --- |
| 运行名 | `ref1`（参照组第 1 轮；D、P 也放在这个运行目录下） |
| 读者 | pi 1.2.0，`sglang/qwen3.8-27b`，思考级别 medium，上下文 262144，压缩预留 32768，与其他读者相同 |
| 命令 | `pi -p --offline --mode json --no-tools --no-mcp --no-skills --no-extensions --no-context-files --no-prompt-templates` |
| 沙箱 | 与其他读者相同，`/work` 为空；C 不带工具，不必等断网转发做好，网络共享即可 |
| 服务与并发 | 独占一台推理服务，12 路并发（10-21 改；原为 4 路） |
| 次数 | 1 次（10-21 改；原提议 2 次），每条记录带 `rep` |
| 上限 | 60 分钟（不带工具，实际不会触发）；单次回复的输出上限 98304 token（§7 第 4 条） |

**启动方式**〔已确认 2026-10-21，已实现〕

与正式时间线（`python -m pweval.harness.timeline <运行名> …`）同一风格，新增参照组的入口：

```text
python -m pweval.harness.refs ref1 --groups C [--reps 1] [--probes main|aux|all] [--ids <题号,…>]
    [--limit N] [--llm <服务地址>] [--dry-run]
```

- `--groups` 可取 `C`、`D`、`P` 的任意组合，按 C → D → P 的顺序运行；`--dry-run` 只生成提示语、不调用模型，用来检查 Final answer 段与段落。
- 续跑与正式时间线相同：同一条命令，已答的（题，次）跳过；`run.yml` 记下仓库与题库的提交、pi 版本、实际生效的配置与服务地址。
- 另在 `eval/pyproject.toml` 中登记命令行入口（例如 `pweval-refs`），等价于上面的写法。
- 正式运行：`pweval-refs ref1 --groups C --reps 1`，2026-10-21 12:15（UTC）开始。
- 并发与次数的取舍：
  - 12 路：服务的 KV 缓存为 530,920 token，试跑中每题的上下文为 9k–38k token，按每路 4 万计 12 路仍在容量内；12 路时合计生成约 766 token/s，4 路时约 330 token/s，单路约 100 token/s。C 的用时不进成本比较，并发不影响作答内容。
  - 1 次：C 只是 H0 的下限，不进非劣效检验；全部 206 题各答一次，既给出 H0 所需的组均值，也能逐题标出“闭卷可答”的题。
- 先导的读者框架中已有闭卷参照线（`eval/src/pweval/harness/readers.py` 的 `--baselines`），可沿用其中的会话调用；提示语、Final answer 段与输出格式按本节改写。

**输出**

- 写到 `~/pw-lab/runs/ref1/answers/C/k30.jsonl` 与 `k30-aux.jsonl`，字段与其他读者相同（`arm` 记为 `C`，另有 `rep`）。判分与其他组同一流程、同批盲判；C 可以先判（§7 第 2 条）。

**怎么读结果**

- 理想情况是闭卷组几乎拿不到分：这批题必须靠材料才能答，其他组的分数来自材料。
- **闭卷可答的题：** 闭卷组得满分或高分的题列为“闭卷可答”，主检验报告含与不含这些题的两种结果。
- **部分分从哪里来：** 闭卷组在要点题上拿到的部分分，先查是否来自泛泛的常识（如“用 MSE 评测”）；若是，说明判分说明对这类要点过松，记为题库问题，不改冻结的题与金标准。
- P 与 C 的差即 H0：差距不显著时，H1 的非劣效检验没有意义（§6）。
