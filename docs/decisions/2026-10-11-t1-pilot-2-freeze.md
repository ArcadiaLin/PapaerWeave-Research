## 1. 写入时间线

- 语料：时序预测 2 篇种子 + 8 篇写入论文，见 [`2026-10-10-t1-pilot-corpus.md`](2026-10-10-t1-pilot-corpus.md)。
- 写者：`writer-i3`（I3，整理结果）与 `writer-i2`（I2，理解机制），每篇论文各一次 pi 会话，先后顺序逐篇交替。
- **版本事件**：FiLM 的写者拿到 v3（`papers/2205.08897v3`）。检查点 2 之后插入一次维护者会话
  （`paper-maintainer`，独立身份 `paper.maintainer@forecast-lab.example`），任务是把库中关于 FiLM 的内容更新到
  v4。v4 的目录在事件开始前才放入各组的论文副本，之前没有会话能看到它。
  v3→v4 改动了：
  - 主表 Exchange 一行，例如 720 步 MSE 从 0.536 改为 0.727；
  - 附录 Table 11 的 ETTm2 一行。v3 中这一行与主表不一致，v4 改成一致。

  语料中没有后来的论文引用 FiLM。
- 每组 17 个会话：16 个写者会话加 1 个事件会话。每 2 篇论文存一个检查点，共 4 个，事件会话位于第 9 个槽位。
- 模型：Qwen3.8-27B，经两个配置相同的 sglang 服务副本。本条时间线 A3 用 :30000、A0 用 :30001，
  下一条时间线两组交换。思考关闭，上下文 262144，会话时限 60 分钟。
- **工具时限（运行中加入，两组相同）：** 单个 shell 工具命令运行超过 10 分钟即终止，pi 收到出错结果后继续
  工作（`t1.sandbox.TOOL_LIMIT_S`，被终止的命令记在会话记录的 `tool_kills` 中）。
  起因是 pilot-2 的 A3 第 1 个会话：写者的脚本中有一句 `while …: pass`，陷入死循环。没有这个时限，就要等到
  会话超时，整次会话作废。
  这一次在规则生效前由 Claude 按同一时限手动终止，见运行目录的 `interventions.jsonl`。

## 2. 读者探针

- 20 个探针，A1–G2。G1、G2 是版本事件探针，金标准按检查点分版本：检查点 ≤ 2 用 v3 的值，≥ 3 用 v4 的值。
- 一个探针在其金标准最早涉及的论文写入后的检查点起有效。各检查点的有效探针数依次为 3 / 13 / 18 / 20。
- 两种读者条件：
  - `store_only`（主测量）：没有论文。A3 的 ReadEvidence 只读产物文档；2026-10-12 之前整个隐藏，见 §6；
  - `with_papers`（辅助）：读论文不阻止，事后审计。

  读者对库只读。
- 读者回答末尾给出 `claims` 清单，判分只认这个清单：
  - **召回**：（论文, 方法, 数据集, 预测长度, 指标, 数值）成对对上才算；
  - **精确率**：每条对照原文结果表核对，状态为 supported / misattributed / unsupported / outdated /
    unknown_paper / unchecked。`outdated` 指所称版本中没有、同一论文的另一版本中有。
    只写简称时按检查点时的当前版本核对。

  要点（rubric）由判分者填写。
- 参照线：闭卷与神谕（神谕附表头）。

## 3. 库健康度（每个检查点，只读，两组同一口径）

1. **有据层忠实度**：按所引版本核对，另核锚点行。新增 `versions`，统计仍引用旧版本的数值，以及其中当前版本
   已改动的。
2. **悬空引用率**。
3. **覆盖他人内容**：分为 value 与 text 两类，text 类待标注。
4. **重复实体候选**：待标注。

## 4. 本次冻结前对 A3 的机制改动（用户 2026-10-11 同意）

- **论文新版本**：Commit 给已有材料的论文写一个新的 `material`，新材料挂到论文上。旧材料保留，并标上
  `superseded_by`。已有引用按材料 id 固定在旧版本上。
- **`_stale` 新增原因 `superseded`**：产物读过的材料已被同一论文的新版本取代。
- **`_revised`**：Traverse 的记录视图与 Search 的 Content 结果带最近一次修订（commit、by、at、reason、anchor），
  在读取时从提交元数据推算。
- **产物数据块中的来源引用写成材料 id**（`pin_sources`）。原先保留写者的 `paper_x::…` 写法，论文换版本后会
  解析到新版本的行。pilot-1 的产物有 672 处这种写法。
- MCP 工具说明同步：Traverse 说明以 `_` 开头的只读字段，Commit 说明怎样记录论文新版本。

A0 没有对应的机制改动：A0 的写者用 git 与笔记，自行决定怎样处理新版本。

## 6. 时间线

两条时间线同一协议、同时运行，只有基础设施不同（`run.yml` 的 `overrides`）：

| 运行 | A3 图库 | A3 服务 | A0 服务 |
| --- | --- | --- | --- |
| `pilot-2` | 7689 | :30000 | :30001 |
| `pilot-2-r2` | 7690 | :30001 | :30000 |

每个服务上各有一条 A3 和一条 A0 的会话流，负载在两组之间对称。7690 本是 e09 DB 测试用的库：r2 运行期间，
这些测试会因库非空而跳过；跑完、测完健康度后，先导出（`A3/neo4j-export.jsonl`）再清空。

**2026-10-12 00:40 前后，两条时间线都因宿主内存不足被 Claude Code 终止。** 本机共 7.8 GiB 内存，3 个 neo4j
约占 2.4 GiB；当时两条时间线各有 4 个并发读者，每个读者带一个 pi 进程，A3 读者另带一个 MCP 服务进程。
终止时的状态：

- `pilot-2`：两组 8 个写者会话完成，检查点 2 已存档；检查点 2 的读者在跑，一条都没记录。
- `pilot-2-r2`：两组 4 个会话完成，检查点 1 已存档；A3 的检查点 1 读者完成了 2 条。A0 第 5 个会话被打断，
  留下的未提交改动已存为补丁并丢弃，见 `interventions.jsonl`。

终止时两个库都停在最后一个检查点上，读者只读，库没有被弄脏。之后的改动：

- `probe_workers` 从 4 降为 2；
- 续跑时，若一个已完成的槽位带检查点、且下一个槽位还没开始，先补齐这个检查点的存档与读者。原先这种情况下
  会跳过它，读者就漏掉了。

按工具规则，被终止的运行由用户决定何时重启。

**2026-10-12 续跑与读取面修正（用户同意）。** 7690 原是 `docker run --rm` 起的一次性容器，WSL 重启后容器
没了，但镜像自带的匿名数据卷留了下来。用同一个卷重建了容器（不再加 `--rm`），图完好，头部在 `commit_000016`。

续跑后给检查点 2 判分时发现，A3 的 `store_only` 读者读不到任何产物文档：

- 沙箱从没挂产物文档目录；
- Search 的说明却写着产物文档“可以直接读”；
- 读者又隐藏了 ReadEvidence。

按设计，产物存在集中式的库中，ReadEvidence 是读产物文档的唯一途径。pilot-2 检查点 2 的 16 个 A3 `store_only`
读者会话里，9 个尝试读、8 个失败。修正如下：

- `store_only` 的 A3 读者保留 ReadEvidence，但只能读产物文档（`E09_EVIDENCE_SCOPE=artifacts`），引用落到论文
  材料时返回 `missing`；
- Search 与 ReadEvidence 的说明改为“产物文档经 ReadEvidence 读”，对写者同样生效；
- A0 不变：读者拿到各自完整的库、拿不到论文，这一点两组已经对等，访问方式的差别属于架构本身。

两条时间线都停下来换上新设置：

- `pilot-2`：停在 A3 第 11 个会话之后，A3 第 1–11 个会话用旧说明、第 12 个起用新说明；
- `pilot-2-r2`：停在检查点 2 的读者中间，已记录的 4 条 A3 读者结果移到 `probes-superseded.jsonl`，在同一图状态上
  重跑。

检查点 1–2（r2 为检查点 1）的 A3 读者结果保留，标为“受缺陷影响”，单独报告。

同时修了续跑的一处漏洞：原先只在 A0 会话结束后丢弃未提交的改动，被中途终止的会话留下的改动会进入重跑的会话。
现在每个 A0 会话开始前也丢弃一次，存为 `*.interrupted.leftover.patch`。

详见两个运行目录的 `interventions.jsonl`。

## 7. 运行顺序与检查

先跑到检查点 1（`--limit 4`），检查会话退出码、超时、请求出错、探针与健康度后，再跑完整条时间线。之后的
每次运行都要检查超时会话数：两组的服务速度不同，只可能经超时影响结果。
