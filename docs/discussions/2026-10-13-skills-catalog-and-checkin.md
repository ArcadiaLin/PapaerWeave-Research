# Skill 进入核心：目录层、统一检入与核心 / 扩展的划分

> **状态：** 2026-10-13 讨论稿，汇总当天几轮讨论。标 **[已商定]** 的已与用户商定，标 **[提议]** 的待定。未改代码与其他设计文档；连锁改动见第 11 节，待本稿定了再动。
>
> 起因：标题改为 *Collaboration without Coordination: Managing Scientific Memory for Agentic Research* 之后，叙事进入 agent memory 的谱系。在这个谱系里，固化的知识只是研究对象之一，更重要的是可复用的经验与工作方法，而 skill、workflow 正是承载这类 memory 的主要对象。
>
> **已定：**
> - skill 进入**核心**，v1 就包含它的最小核心（第 4 节、第 10 节）；
> - 产物写入统一为一个 `CheckIn`，不再每类一个工具；产物类型由“库执行的契约”与“agent 遵循的 skill”组成（第 5 节）；
> - 写入只有一种模式：按类型契约检入。Commit 也是一种检入，区别只在存法：Commit 把文档拆进图，`CheckIn` 原样保存文档。paper-form 也有 skill。v1 实现上保留 `Commit` 与 `CheckIn` 两个工具（第 5.3 节）；
> - 库一侧不再叫 operator：读的一组叫访问方法，写的一组统称检入（第 6 节）；
> - 项目视图是**扩展**，只读，用核心组合出来；带范围的原生 Search 推迟（第 8 节）；
> - 分层对照表作为整体逻辑的顶层抽象，留在文档中，用来核对有没有漏层；论文仍按任务的逻辑叙述，不硬套这张表（第 2 节）；
> - A0 不给 skill（第 10.2 节）。

## 1. 两种 memory，两种一致方式

叙事草稿原有一刀：过程性经验以使用效果评判，声明性的研究知识以来源评判；并写过“我们存的不是经验，是知识与产物”。纳入 skill 之后，这句改为：**两种都存，按不同的规则管**。

| | 声明性：论文知识、共同产物 | 过程性：skill |
| --- | --- | --- |
| 内容 | 论文说了什么，写者判断了什么 | 怎样用库完成一类研究任务 |
| 权威来源 | 论文原文、外部标识 | 执行证据：哪些会话按它做过，写下的内容事后是否通过审计 |
| 身份 | 外部标识、自然键 | 意图或任务模式（键的取法见第 12 节） |
| 写入时校验 | 引用、出处、键 | 声明的依赖存在：用到的工具、产物类型 |
| 过时 | 输入被修订，材料换了版本 | 依赖的工具契约或产物类型升级 |

库只记录执行证据，不按使用次数排名，判断留给读者。这延续“可问责，而非权威”。

## 2. 顶层抽象：与 DBMS 分层的对照

**[已商定]** 这张表用来核对整体逻辑有没有漏层，不作为论文的叙事主线。论文按任务的逻辑讲，需要时引一两个对应。

| DBMS 的层 | 经典 | PaperWeave |
| --- | --- | --- |
| 查询 | SQL、代数表达式（声明式，说要什么） | 意图、读者的问题（自然语言） |
| 优化器 | 选执行计划 | agent 规划，以 skill 为模板 |
| 计划缓存、计划基线 | 为一类查询保存已接受的计划；新计划要有执行证据才被接受；结构变化即失效（如 Oracle SQL Plan Management） | **skill**：带执行证据，依赖的契约或类型变化即过时 |
| 关系算子 | filter、join、group by | **agent 执行的语义算子**：可比性、同一性、支持与否。谓词是语义的，库算不了 |
| 访问方法 | 索引扫描、按键查找、导航、取元组 | Search、Resolve、Traverse、ReadEvidence、FetchArtifact |
| 物化视图 | 保存查询结果，基表变化即失效 | **Artifact**：语义查询的物化结果，带 `USED` 谱系与 `_stale` |
| 写入与日志 | DML、写前日志、审计日志 | Commit、`CheckIn`、graph-vc；访问日志待补（第 7 节） |
| 目录 | 系统目录（Codd 规则 4：元数据用同一模型存储） | 产物类型定义、skill |

由此得到一句概括：**agent 是查询处理器；库管理它的输入（访问方法与检索面）、输出（物化的产物）和计划（skill）。** 这与职责边界一致。

**查询表达式、执行计划与 skill 的区别：** 查询表达式是声明式的；执行计划是优化器选定的物理算子组合，顺序固定，通常是树，有公共子表达式时是 DAG。skill 二者都不是：它写的是怎么做，但含条件分支与重试，分支取决于语义判断（覆盖够不够，检入被拒后重取）。所以 **skill 是带控制流的计划模板，它的每一次执行留下一张 DAG**，即访问日志中实际发生的调用序列。论文中 skill 需要时称 workflow 或 plan template，“DAG”只指执行记录。

**要预先回答的追问：** 为什么不像 LOTUS、Palimpzest 那样做声明式查询加内置 LLM 的语义算子？那类系统的语义判断在系统内部完成，无人负责；我们把判断留给写者，库保存判断的依据与谱系。研究任务的计划还要在步骤之间按判断改道，事先编不成固定计划。回到导航式访问要讲清这两条理由，否则会被读成倒退。

## 3. 核心与扩展

**[已商定]** 论文的核心要讲一整套；能支持、但不闭合的东西作为扩展，按所支持的工作负载来讲。

一项机制进入**核心**，须同时满足：

1. 问题或标题要求它，缺了故事不完整；
2. **闭合**：全部核心机制（身份、版本、来源、写入时校验、过时）都作用于它，它也不依赖核心之外的机制；
3. 进入主评测，写成主张。

不满足、但能完全由核心组合出来的是**扩展**。**扩展只往目录里加条目（一个产物类型加一份 skill），不加机制。** 扩展只做演示，说明核心够用，不写成主张。

| 归属 | 内容 |
| --- | --- |
| 核心机制 | 身份、版本、来源、写入时校验、过时；数据、目录、日志三块 |
| 核心实例化的产物类型 | Leaderboard、CompareSettings、Verify、Summarize、Generate，由 I1–I6 推出，与领域词表同属工作负载的实例化 |
| 扩展 | ProjectView 类型加项目视图 skill（第 8 节） |

## 4. Skill 进入核心：闭合条件

**[已商定]** skill 进核心，因为 Scientific Memory 要求经验。要满足闭合，下面每项都要成立：

| 核心机制 | 作用于 skill | 需要补的 |
| --- | --- | --- |
| 身份 | 按意图或任务模式加身份键 | 键的取法（第 12 节） |
| 写入时校验 | 声明依赖的工具与产物类型必须存在 | 产物类型定义进目录（第 7 节） |
| 版本 | 与产物一样检出、编辑、检入 | 复用 `CheckIn` |
| 来源 | 形成者；执行证据：哪些会话取用了哪个版本，之后写下了什么，事后是否通过审计 | 访问日志进库（第 7 节） |
| 过时 | 依赖的工具契约或产物类型升级后标为可能过时 | 工具版本已有 `_op_version`；产物类型定义的版本待补 |
| 发现（C5） | 读者能按意图找到别人写下的 skill；取出后写进工作区供 pi 加载 | Search 覆盖 skill；取出照 FetchArtifact 的做法 |

**最真实的例子是 paper-form 的 skill。** 写者最主要的工作是读一篇论文、写出 paper-form，这本身就是一份 skill，现在散落在 [抽取原则](../designs/v2/extraction_principles.md)、表单模板与示例、Commit 的工具描述三处。paper-form 已从 v1 演进到 v4，每次升级，按旧版写的做法就过时了。这是我们自己踩过的情形，不是为演示编出来的。

**写 skill 谁都会，库给的是什么：** 写 skill 是语义工作，归 agent（用户让它写，或它自动形成），职责边界不变。只有放进库里，skill 才有写入时的校验、从访问日志还原的执行证据，以及工具升级后的过时提示。这是 skill 文件夹做不到的。

**与打包格式的区别：** 把 skill 与 MCP 工具打成一个分发单元（如 Claude Code 的 plugin，以及用户提到的 OpenAI 的同类协议，引用前须找到原始出处）解决的是分发：作者写好，用户装上。我们的区别在状态：skill 由写者在工作中写、改、积累，本身是库中有版本、有证据、会过时的数据；检入产出的 artifact 由库接管，可检索、进入图谱、带谱系；而且多个使用者共享、互不协调。

## 5. 统一的写入模式：按类型检入

### 5.1 产物类型与 `CheckIn`

**[已商定]** 现有产物“算子”本来就共用一个工作模式：取出文档，按格式编辑，带 `base` 检入，库校验键与引用、保存新版本、在读取时计算过时（[算子契约](../designs/v2/operators.md) §4.1）。这是机制，属于核心。各类型不同的只有两样：

| 每个类型不同的部分 | 内容 | 谁执行 |
| --- | --- | --- |
| 契约 | 身份键、行键、引用规则、检入时的检查 | 库，在检入时执行 |
| skill | 怎样做出这类文档：先查什么，哪里要判断，何时回读原文 | agent，自行遵循 |

$$
\text{skill（怎么做）} + \text{CheckIn（按类型契约校验）} \Rightarrow \text{artifact}
$$

- **产物类型**（artifact type）= 契约 + skill，接近对象关系模型中结构、约束与操作定义在一起的用户自定义类型。
- **工作模式**就是**检出—检入**（check-out / check-in），出自工程设计数据库的长事务与版本模型（常引 Katz 1990 关于工程数据库版本建模的综述，写入论文前核对）。它已在经典机制清单中，对应 C4。
- **统一为一个 `CheckIn`**：类型从文档头部读出，契约按类型从目录取。以前每类一个工具，是因为工具描述是唯一的引导渠道；skill 接管类型特有的用法之后，不再需要。新增类型只加一条契约和一份 skill，不加工具，正符合扩展的定义。代价是 agent 从工具列表看不出有哪些类型，要靠 skill 列表与 Search 发现。
- skill 本身也经 `CheckIn` 写入，类型为 skill。
- 这不改变 operator 的叙事，只是把它说准：产物“算子”从来不计算内容，计算内容的是写者；它做的是带类型的检入。不给 operator，只给 skill，写出来的就只是一个文件（即 A0 的情形）。

### 5.2 Commit 也是一种检入：拆开存与原样存

**[已商定]** Commit 的流程与 `CheckIn` 是同一个模式（[草稿文件](../designs/v2/draft_files.md)、[Commit 契约](../designs/v2/commit_contract.md)）：写者在工作目录写一份 graph-doc（`doc_file`）；库按 schema 与 `NameKey` 校验，有阻塞项（查重候选、修订缺锚点）就退回写者；写者改完再交；库写入，形成一个 graph-vc 提交。两者唯一的区别是交上来的文档进库后怎样存：

| | Commit | `CheckIn` |
| --- | --- | --- |
| 文档类型 | paper-form、supplement-form | Leaderboard、CompareSettings、Verify、Summarize、Generate、skill |
| 进库方式 | **拆开存**：文档分解为图中的节点与边，文档本身只留在提交记录里 | **原样存**：整份文档作为一个版本保存，图里只放锚点（身份键、`USED`） |
| 身份 | 逐条记录收敛（`NameKey`、查重候选） | 整份文档一个身份键 |
| 改他人的内容 | 有据层修订须带锚点与理由 | 改他人的行须写理由 |
| 版本冲突 | 按记录的改前值核对 | 按整份文档的 `base` 核对 |

经典对应是 XML 进关系库的两种存法：拆成关系表（shredding），或作为原生文档保存。它也就是“薄图、厚文档”：

- 需要逐条去重、逐条修订、被他人引用的内容，**拆开存进图**，即 Entity、Concept、Content；
- 整份才有意义、靠共同编辑维护的内容，**原样存为文档**，即 Artifact。

所以写侧统一为一句：**只有一种写入模式，即按类型契约检入；每个类型规定自己的存法，拆开或原样。** 四类对象与两种存法的对应，也说明了元模型为什么是这四类。

由此目录中的条目齐全：

| 目录条目 | 内容 | 存法 |
| --- | --- | --- |
| 图的类型 | 领域词表与 `NameKey` 规则 | 拆开存的契约 |
| 表单 | paper-form、supplement-form | 拆开存 |
| 产物类型 | 五个核心类型；ProjectView 作为扩展 | 原样存 |
| skill | 每个表单、每个产物类型各一份 | 原样存（skill 本身也是经 `CheckIn` 写入的文档） |

### 5.3 实现：v1 保留两个工具

**[已商定]** 论文与文档中讲一种写入模式、两种存法；v1 的 MCP 工具仍是 `Commit` 与 `CheckIn`。理由：

- Commit 已经实现并测过，v1 不返工；
- 两个工具名正好标出两种存法。

合并成一个入口（从文档头部读出类型，paper-form 走拆开的路径，内部调用现有的 Commit 代码）留到投会议、实现稳定之后。合并时还要对齐交互流程：Commit 有阻塞项就退回、没有就直接写入；`CheckIn` 先校验，带 `confirm` 才写入（[草稿文件](../designs/v2/draft_files.md) §7 说明了两者为何不同）。

## 6. 命名

**[已商定]** 库一侧不再叫 operator：在数据库里 operator 指计算，而按第 2 节，计算由 agent 做。

| 层 | 名字 | 包括 |
| --- | --- | --- |
| 读 | 访问方法（access methods） | Search、Resolve、Traverse、ReadEvidence、FetchArtifact |
| 写 | 检入（check-in），按类型契约 | 拆开存：`Commit`（paper-form、supplement-form）；原样存：`CheckIn`（产物与 skill）。v1 为两个工具（第 5.3 节） |
| 目录 | 产物类型（契约）、skill | 五个核心类型；ProjectView 作为扩展 |
| agent 的判断 | 语义算子（只在第 2 节的分层表中用） | 可比性、同一性、支持与否 |

## 7. 目录层、访问日志与 DBMS 清单

按 DBMS 自身保存与管理的东西逐项对照，找出缺口：

| DBMS 管的东西 | PaperWeave 现状 | 判断 |
| --- | --- | --- |
| 用户数据 | Entity / Concept / Content / Artifact | 有 |
| 目录：schema 与约束 | 领域类型、`NameKey` 规则、表单、产物身份键与行键，写死在代码与文档中 | **缺口：类型、表单与产物类型的定义进目录，带版本**（第 5.2 节） |
| 目录：视图定义 | 没有 | 扩展（第 8 节） |
| 目录：存储过程 | 没有 | skill（第 4 节） |
| 目录：触发器、主动规则 | 没有；过时在读取时计算，Commit 返回相关产物算写入时提示 | 有意不做：派生内容由 agent 生成，重算昂贵且不确定，只失效不维护，与视图失效同一条理由 |
| 目录：用户、角色、权限 | 只记谁写的，不管谁能写 | **缺口，论文中明确排除**：处理的是协作写者的语义正确性，不是恶意写者 |
| 日志 | graph-vc 记录每次写入的前后值；读与工具调用只在会话轨迹中 | **缺口：访问日志进库**，作为 skill 执行证据的来源 |
| 索引与访问结构 | 检索面、全文与向量索引 | 有 |
| 统计信息与优化器 | 计划由 agent 做 | 有意不做（职责边界） |
| 事务与并发控制 | 写者轮流执行 | 有意不做（不协调是语义上的） |

**[提议]** 核心因此由三块组成：数据（四类对象）、目录（产物类型定义、skill）、日志（写日志已有，访问日志新增）。

另一个可借的框架是 Ground（Hellerstein 等，CIDR 2017）把数据上下文分为 Application、Behavior、Change 三类（表述待回原文核对）：A 对应元模型与身份；B 对应来源、`USED`，以及 skill 与访问日志；C 对应 graph-vc 与产物版本。按这个框架，目录层与访问日志补齐的是 B 类。

ANSI/SPARC 三级模式是另一个维度：外模式对应项目视图，概念模式对应元模型与领域类型，内模式对应 Neo4j、材料文件与 graph-vc。

## 8. 项目视图：扩展

**[已商定]** 不再用 fork / merge 的说法与做法。

`project_views.md`（2026-10-08）的设计是每个项目一个 Neo4j 实例，在项目内积累后回流。逐项对照经典视图：内容（抽取的子图）、投影（排除部分关系）、自有索引与排序都对得上物化视图；对不上的是三处：

- 定义是 agent 执行 skill 的结果，没有存进库，库判断不了它是否过时、是否缺了新内容；
- 描述写在 `AGENTS.md` 等记忆文件中，在库外，会漂移；
- 允许本地写、之后回流，这在数据库里是副本或分支，不是视图，绕不开合并。

**做法：只读，用核心组合出来。**

- **项目视图 skill**：agent 判断范围（哪些任务、论文，排除哪些关系类型），用 Search、Traverse、FetchArtifact 把选中的子图取到工作区，在 `AGENTS.md` 中写一段说明并给出视图 id；
- **ProjectView 类型**：视图定义写成文档经 `CheckIn` 登记，可混合外延式（列出纳入的 id）与内涵式（按任务、数据集取对象，沿某些关系扩展，排除某些关系类型）。文档中的引用形成 `USED`，纳入的对象被修订时，视图卡被标为可能过时，过时提示由核心直接给出；
- 新写入一律检入总库；“在别人的成果上继续做”由共同编辑的产物覆盖。

**推迟：** 把视图做成访问方法的范围参数（如 `Search(..., view=<view_id>)`），库内只有一份数据，不另建实例、不跨库分配 id、不存在回流。工作量较大，作为以后的增强。

## 9. 对实验设定的影响

现行设定是默认配置的 pi，用法只写在 MCP 工具描述中。加入 skill 后，用法多了 skill 这条渠道。pi 原生从工作目录加载 skill，仍属默认配置，但需核实：

- pi 从哪个目录、以什么格式加载 skill；
- 加载能否被观察到。只有经 MCP 取用才会进访问日志，执行证据才能闭合。

## 10. 评测

### 10.1 v1 的 skill 最小核心

**[已商定]** v1 包含 skill 的最小核心。

| 项 | 内容 |
| --- | --- |
| skill 的形式 | 一份文档，正文沿用 pi 能加载的 skill 格式；头部声明身份键（意图或任务）与依赖（用到的工具、产物类型） |

### 10.2 A0 不给 skill

**[已商定]** A0 不给 skill。这与已商定的“A0 拿到种子 Leaderboard，但不附要求统一维护的提示；统一的格式是 A3 的机制之一”（[评测草案](../designs/v2/evaluation_draft.md) §2.2）是同一条原则：skill 是核心的一部分，A0 不拿。

由此带来的边界要如实写出：A0 与 A3 的差别是**整个系统**（包括 skill）对文件加 git 的差别，v1 不区分其中哪一部分起作用。归因靠消融：

- **−skill**：有 `CheckIn`、没有种子 skill，A3 与它之差是 skill 的作用；
- **−共同编辑**（已有）：去掉检出—检入，看机制本身的作用。

**[提议]** 投会议时再加一个稳健性组 **A0+skill**：文件加 git，配上种子 skill 的文件版（同样的步骤，改用文件与 git 完成）。它回应“优势只是来自提示词”这一最直接的质疑：如果 A0 拿到同样的做法仍然更差，差距就来自库。
