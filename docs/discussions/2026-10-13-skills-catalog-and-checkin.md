## 1. 重心：一个主张

**[提议]** 论文只立一个主张，其余机制都为它服务：

> 不协调的 agent 写者共享一份记忆时，错误会悄悄累积；靠锚点与署名，而不是靠系统内部的裁决，可以防住这种退化。

- **区分点在裁决位置。** 主流 agent memory（Graphiti、Mem0 一类）由系统内部的 LLM 合并、去重、判定矛盾并改写记忆；我们不在系统内部裁决：有据层对照原文锚点，解释层的判断带着写者与输入并存，可能的重复退回写者确认。
- **长板取决于数据。** 机制各有经典前身，单独都不构成长板。能成为长板的是 E1：写者增多时文件加 git 悄悄退化，PaperWeave 挡住。这一点要靠运行结果证明；不显著时按负结果收窄主张（[评测草案](../designs/v2/evaluation_draft.md) §12）。
- **贡献收为三条：** 现象与工作负载；对应的写入语义（身份收敛、有据层对照锚点修订、解释层并存、共同产物有版本可追溯）；证据。版本、检入、过时、skill 写进设计章节，不单列为贡献。
- **完整不是长板。** DBMS 对照（第 6 节）和机制的经典前身放在设计理由与相关工作中，不作为叙事骨架。

## 2. Skill 是一种产物类型

**[已商定]** 库存两层内容，skill 落在其中一层，不另立规则：

| | 有据层 | 解释层 |
| --- | --- | --- |
| 内容 | 论文所说：实体身份、`stated_by: paper` 的记录 | 写者所判、所做：Observation、`stated_by: agent` 的记录与正反关系、产物；**skill 是产物的一种** |
| 怎样一致 | 对照原文锚点：单值，修订须附锚点与理由 | 不要求一致：带写者与输入并存，有键的产物共同编辑 |
| 库不做的事 | 不替写者判断原文的意思 | 不评判、不排名 |

skill 与其他产物同一套规则：写者是谁（形成者、编辑者），依据什么（文档中的引用形成 `USED`），怎样共同维护（按身份键检出、检入），何时可能过时（依赖变了）。库只记录，不评判哪份 skill 好用，延续“可问责，而非权威”。

$$
\text{skill}_{t} + \texttt{CheckIn} \Rightarrow \text{artifact}_{t}, \qquad t \in \{\text{paper-form}, \text{Leaderboard}, \dots, \text{Skill}\}
$$

- 每个类型的 skill 说明怎样做出这类文档：先查什么，哪里要判断，何时回读原文。Skill 类型自己也有一份 skill，说明怎样写 skill。新增类型只在目录中加一条契约与一份 skill，不加机制。
- **不说“经验”。** 把所有内容都称为经验会抹掉有据层，也会回到已被取代的“单 agent 经验复用”叙事。论文中说“写者写下的做法与写下的结果按同一套规则管理”。
- **最真实的例子是 paper-form 的 skill。** 写者最主要的工作是读一篇论文、写出 paper-form，这本身就是一份 skill，现在散落在[抽取原则](../designs/v2/extraction_principles.md)、表单模板与示例、Commit 的工具描述三处。paper-form 从 v1 演进到 v4，每次升级，按旧版写的做法就过时了。
- **与打包格式的区别：** 把 skill 与 MCP 工具打成一个分发单元（如 Claude Code 的 plugin，以及 OpenAI 的同类协议，引用前须找到原始出处）解决的是分发；这里的 skill 是写者在工作中写、改、共同维护的数据，有版本、有署名。
- **附带的观察：** 写者在运行中可能改坏别人写的 skill。这是主命题的一个实例，由版本与署名兜住；只描述现象，不另立主张。

## 3. 统一的写入模式：按类型检入

### 3.1 产物类型与 `CheckIn`

**[已商定]** 现有产物“算子”本来就共用一个工作模式：取出文档，按格式编辑，带 `base` 检入，库校验键与引用、保存新版本、在读取时计算过时（[算子契约](../designs/v2/operators.md) §4.1）。各类型不同的只有两样：

| 每个类型不同的部分 | 内容 | 谁执行 |
| --- | --- | --- |
| 契约 | 身份键、行键、引用规则、检入时的检查 | 库，在检入时执行 |
| skill | 怎样做出这类文档 | agent，自行遵循 |

- **产物类型** = 契约 + skill，接近对象关系模型中结构、约束与操作定义在一起的用户自定义类型。
- **工作模式**是检出—检入，出自工程设计数据库的长事务与版本模型（常引 Katz 1990，写入论文前核对），对应 C4。
- **统一为一个 `CheckIn`：** 类型从文档头部读出，契约按类型取。以前每类一个工具，是因为工具描述是唯一的引导渠道；skill 接管类型特有的用法之后，不再需要。代价是 agent 从工具列表看不出有哪些类型，要靠 skill 列表与 Search 发现。
- 产物“算子”从来不计算内容，计算内容的是写者；它做的是带类型的检入。只给 skill、不给检入，写出来的就只是一个文件，即 A0 的情形。

### 3.2 Commit 也是一种检入：拆开存与原样存

**[已商定]** Commit 的流程与 `CheckIn` 是同一个模式（[草稿文件](../designs/v2/draft_files.md)、[Commit 契约](../designs/v2/commit_contract.md)）：写者在工作目录写一份 graph-doc，库校验，有阻塞项就退回，写者改完再交，库写入并形成一个 graph-vc 提交。区别只在交上来的文档进库后怎样存：

| | Commit | `CheckIn` |
| --- | --- | --- |
| 文档类型 | paper-form、supplement-form | Leaderboard、CompareSettings、Verify、Summarize、Generate、Skill |
| 进库方式 | **拆开存**：分解为图中的节点与边，文档本身只留在提交记录里 | **原样存**：整份文档作为一个版本保存，图里只放锚点（身份键、`USED`） |
| 身份 | 逐条记录收敛（`NameKey`、查重候选） | 整份文档一个身份键 |
| 改他人的内容 | 有据层修订须带锚点与理由 | 改他人的行须写理由 |
| 版本冲突 | 按记录的改前值核对 | 按整份文档的 `base` 核对 |

经典对应是 XML 进关系库的两种存法：拆成关系表（shredding），或作为原生文档保存。它也就是“薄图、厚文档”：需要逐条去重、逐条修订、被他人引用的内容拆开存进图（Entity、Concept、Content）；整份才有意义、靠共同编辑维护的内容原样存为文档（Artifact）。四类对象与两种存法的对应，说明了元模型为什么是这四类。

### 3.3 实现：v1 保留两个工具

**[已商定]** 论文与文档中讲一种写入模式、两种存法；v1 的 MCP 工具仍是 `Commit` 与 `CheckIn`：Commit 已经实现并测过，不返工；两个工具名正好标出两种存法。合并成一个入口留到投会议之后，合并时要对齐交互流程：Commit 有阻塞项就退回、没有就直接写入；`CheckIn` 先校验，带 `confirm` 才写入（[草稿文件](../designs/v2/draft_files.md) §7 说明了两者为何不同）。

## 4. 访问方法：按数据模型检查

**[提议]** 访问方法是否够用，不从工作负载出发（I1–I6 能否组合出来只证明够用，不证明完整），而按“库里存的东西 × 访问方式”逐格检查。访问方式取 DBMS 的五种：按键查找、按内容检索、沿关系导航、按 id 读取、按历史时刻读取（SQL:2011 的 `AS OF`）。

| | 按键 / 身份定位 | 按内容定位 | 导航 | 读取 | 历史 |
| --- | --- | --- | --- | --- | --- |
| 图记录（拆开存） | `Resolve`（Entity、Concept） | `Search` | `Traverse` | `Traverse([x])`，重组为 graph-doc | `AsOf`、`Diff`、`Log`、`Show` |
| 产物文档，含 skill（原样存） | **缺（G1）** | `Search(type=Artifact)` | `Traverse` 沿 `USED` | `FetchArtifact`、`ReadEvidence` | `Log(node)`、`FetchArtifact(at)` |
| 材料（原文） | 材料 id | 有意不做：原文全文检索交给文件系统，绕过的读取另行审计 | — | `ReadEvidence` | `ReadEvidence(at)` |
| 写日志 | — | — | — | `Log`、`Show` | — |

- **G1 有身份键的文档没有按键查找。** 读者要找“ETTh1 多变量的那张 Leaderboard”，现在只能从数据集沿 `USED` 反向走再按 `op` 过滤，或去检入、撞键被退回：身份只在写入时执行，读侧没有对应的访问路径。skill 也一样，“这个类型的 skill 是哪一份”是按键查。v1 的最小做法：`Search` 在 Artifact 上加精确匹配的 `key` 条件。
- **G2 历史访问漏在了列表外。** `Log`、`Show`、`Diff`、`AsOf` 与贯穿各接口的 `at` 参数，现在叫“版本记录的读取接口”，按上表就是“历史”一列。访问方法分为两组：当前状态（`Search`、`Resolve`、`Traverse`、`ReadEvidence`）与历史（`Log`、`Show`、`Diff`、`AsOf`）。只改归类，不改代码。
- **G3 `FetchArtifact` 是检出，不是纯读取。** 它写进工作目录、带 `base`，是检入的前一半。两种存法各有一对：

  | | 检出 | 检入 |
  | --- | --- | --- |
  | 拆开存 | `Traverse`：把子图重组为 graph-doc，原样交回 `Commit` 是 `noop` | `Commit` |
  | 原样存 | `FetchArtifact`：原样取出，带 `base` | `CheckIn` |

  XML 拆开存的逆过程是重组（publishing），这里也一样。`ReadEvidence` 仍是纯读取，按行读、可引用。
- **重叠可以接受：** `Search` 的 `where.used` 与沿 `USED` 反向的 `Traverse`、`Traverse([x])` 兼做按 id 读取，都是便捷写法，相当于索引扫描与导航有交集。`Resolve` 与 `Search` 的分界要守住：`Resolve` 返回身份状态（resolved、ambiguous）并承担写入时的查重，是 C1 的机制；`Search` 只做排序检索。
- **有意不做，论文中说明：** 对内容计算（排序、分组、聚合，计算归 agent）；语义谓词（库算不了）；关系检索（没有工作负载需要）；原文全文检索（交给文件系统）。
- **推迟的候选：工作集上的增量读取**，即“自从我上次看过以后，这些对象哪里变了”，经典对应是变更数据捕获与持续查询。v1 由单份产物的编辑提示、`Diff(node)` 与 Commit 返回的相关产物替代。

## 5. 命名

**[已商定]** 库一侧不再叫 operator：在数据库里 operator 指计算，而计算由 agent 做。

| 层 | 名字 | 包括 |
| --- | --- | --- |
| 读：当前状态 | 访问方法（access methods） | `Search`、`Resolve`、`Traverse`、`ReadEvidence` |
| 读：历史 | 访问方法 | `Log`、`Show`、`Diff`、`AsOf`，以及各接口的 `at` |
| 检出 | 检出（check-out） | 拆开存：`Traverse` 的对象视图；原样存：`FetchArtifact` |
| 写 | 检入（check-in），按类型契约 | 拆开存：`Commit`（paper-form、supplement-form）；原样存：`CheckIn`（产物与 skill） |
| 目录 | 产物类型（契约）、skill | 核心类型；ProjectView 作为扩展 |
| agent 的判断 | 语义算子（只在第 6 节的分层表中用） | 可比性、同一性、支持与否 |

检出一行与读的两行是 **[提议]**（第 4 节 G2、G3），其余已商定。

## 6. 顶层抽象：与 DBMS 分层的对照

**[已商定]** 这张表用来核对整体逻辑有没有漏层，不作为论文的叙事主线。论文按任务的逻辑讲，需要时引一两个对应。

| DBMS 的层 | 经典 | PaperWeave |
| --- | --- | --- |
| 查询 | SQL、代数表达式（声明式） | 意图、读者的问题（自然语言） |
| 优化器 | 选执行计划 | agent 规划，以 skill 为模板 |
| 计划基线 | 为一类查询保存已接受的计划，结构变化即失效（如 Oracle SQL Plan Management） | skill：作为产物保存，有版本与署名 |
| 关系算子 | filter、join、group by | agent 执行的语义算子：谓词是语义的，库算不了 |
| 访问方法 | 索引扫描、按键查找、导航、取元组、`AS OF` | 第 4 节与第 5 节 |
| 物化视图 | 保存查询结果，基表变化即失效 | 产物：语义查询的物化结果，带 `USED` 与 `_stale` |
| 写入与日志 | DML、写前日志、审计日志 | `Commit`、`CheckIn`、graph-vc；访问日志推迟（第 11 节） |
| 目录 | 系统目录（Codd 规则 4：元数据用同一模型存储） | 产物类型、skill；skill 已按产物存储，类型定义进库推迟 |

一句概括：**agent 是查询处理器；库管理它的输入（访问方法与检索面）、输出（产物）和计划（skill）。** 这与职责边界一致。

- **查询表达式、执行计划与 skill 的区别：** 查询表达式是声明式的；执行计划是选定的物理算子组合，顺序固定。skill 二者都不是：它写怎么做，但含条件分支与重试，分支取决于语义判断。所以 skill 是带控制流的计划模板，每次执行留下一张 DAG，即会话轨迹中实际发生的调用序列。论文中需要时称 workflow 或 plan template。
- **要预先回答的追问：** 为什么不像 LOTUS、Palimpzest 那样做声明式查询加内置 LLM 的语义算子？那类系统的语义判断在系统内部完成，无人负责；我们把判断留给写者，库保存判断的依据与谱系。研究任务的计划还要在步骤之间按判断改道，事先编不成固定计划。

## 7. 核心与扩展

**[已商定]** 一项机制进入核心，须同时满足：问题或标题要求它；**闭合**，即全部核心机制（身份、版本、来源、写入时校验、过时）都作用于它，它也不依赖核心之外的机制；进入主评测。不满足、但能完全由核心组合出来的是扩展。**扩展只往目录里加条目（一个产物类型加一份 skill），不加机制**，只做演示，不写成主张。

| 归属 | 内容 |
| --- | --- |
| 核心机制 | 身份、版本、来源、写入时校验、过时 |
| 核心实例化的类型 | paper-form、supplement-form（拆开存）；Leaderboard 等产物类型与 Skill（原样存）。由 I1–I6 推出，与领域词表同属工作负载的实例化 |
| 扩展 | ProjectView 类型加项目视图 skill（第 8 节） |

skill 作为产物类型，闭合是自动的：五项核心机制本来就作用于产物。第一版中为 skill 补的执行证据、访问日志与类型定义进库，都不是闭合所必需，推迟到投会议（第 11 节）。

## 8. 项目视图：扩展

**[已商定]** 不再用 fork / merge 的说法与做法。

`project_views.md`（2026-10-08）的设计是每个项目一个 Neo4j 实例，在项目内积累后回流。逐项对照经典视图，对不上的是三处：定义是 agent 执行 skill 的结果，没有存进库；描述写在库外的 `AGENTS.md` 中，会漂移；允许本地写、之后回流，在数据库里是副本或分支，不是视图，绕不开合并。

**做法：只读，用核心组合出来。**

- **项目视图 skill**：agent 判断范围，用 `Search`、`Traverse`、`FetchArtifact` 把选中的子图取到工作区，在 `AGENTS.md` 中写一段说明并给出视图 id；
- **ProjectView 类型**：视图定义写成文档经 `CheckIn` 登记，可混合外延式（列出纳入的 id）与内涵式（按任务、数据集取对象，沿某些关系扩展，排除某些关系类型）。文档中的引用形成 `USED`，纳入的对象被修订时视图被标为可能过时；
- 新写入一律检入总库；“在别人的成果上继续做”由共同编辑的产物覆盖。

**推迟：** 把视图做成访问方法的范围参数（如 `Search(..., view=<view_id>)`）。

## 9. 实验设定：pi 怎样加载 skill

已按 pi 的文档（`docs/skills.md`）核实：

- pi 实现 Agent Skills 规范：一个 skill 是一个目录，内含 `SKILL.md`，头部是 `name` 与 `description`，另可有 `metadata`；
- **启动时扫描**：项目的 `.agents/skills/` 从工作目录向上查找；每个 skill 只把名称、说明与路径放进系统提示，模型按需读取 `SKILL.md` 全文；
- 会话中途新增或修改的 skill 要 `/reload` 才进入列表，但模型仍可直接读文件；
- 现有沙箱只给 pi 模型配置与设置，不带宿主机的 skill（`experiments/t1/src/t1/sandbox.py`）。

由此定下：

- **A3 每次会话开始前**，由运行框架把库中各 skill 的当前版本取到工作目录的 `.agents/skills/<name>/SKILL.md`，相当于对 skill 调一次 `FetchArtifact`；`id`、`base` 写进头部的 `metadata`，不破坏格式；
- 写者改 skill 就是改这个文件，再经 `CheckIn` 检入；
- **可观察性**：模型读取 `SKILL.md` 是一次文件读取，出现在 pi 的会话轨迹中，不经 MCP。v1 从轨迹统计 skill 的读取，不需要访问日志进库。

## 10. 评测

**[已商定]** A0 不给 skill。这与“A0 拿到种子 Leaderboard，但不附要求统一维护的提示；统一的格式是 A3 的机制之一”（[评测草案](../designs/v2/evaluation_draft.md) §2.2）是同一条原则。

由此带来的边界如实写出：v1 中 A0 与 A3 的差别是**整个系统**（包括 skill）对文件加 git 的差别，不区分哪一部分起作用。v1 对 skill 只做描述性统计：各 skill 被读取的会话比例；写者沿用、改写、新写 skill 的情况；是否有人改动了别人写的 skill。不写成主张。

投会议时归因靠两组：

- **−skill 消融**：有 `CheckIn`、没有种子 skill，A3 与它之差是 skill 的作用；
- **A0+skill 稳健性组**：文件加 git，配上种子 skill 的文件版（同样的步骤，改用文件与 git 完成）。如果 A0 拿到同样的做法仍然更差，差距就来自库，回应“优势只是来自提示词”。
