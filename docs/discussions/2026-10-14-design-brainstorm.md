# PaperWeave：研究定位、管理机制与评测口径

2026 年 10 月 14 日头脑风暴整理。

本文整理本轮口头讨论中的问题、回答及其适用边界。仓库参照版本为 `ecb477f0e61e69c9eba6bd3776d91603fdc9e594`（2026-10-13 23:41，北京时间）。它是讨论记录，不表示下述机制均已实现，也不替代仓库中的正式设计或评测协议。

> **2026-10-14 用户决定：** 标题改为 *Collaboration without Coordination: Managing Scientific Knowledge for Agentic Research*（已同步 `AGENTS.md`、`paper/narrative-draft.md`）；Skill 维持 v1 必做类型，砍掉 Skill 类型自己的种子 skill（[待办](../experiments/2026-10-13-arxiv-v1-todo.md) B3）。§4 新增的三项检查（历史重建、引用版本固定、图—文档一致性）只证明实现按契约工作，对文件加 Git 不适用或天然成立，不计入 E1 的组间对比。§6 的强制依赖检查要记录逐项处理结果，属于检查记录，须放开模型冻结，留作投会议的候选。

## 1. Memory 是否把研究范围推得过宽？

**你的问题。** 标题从 scientific knowledge 转向 scientific memory 后，开始倒逼系统纳入 skill、经验整合、遗忘等功能。这些内容超出了原先设计，是否需要收回？

**讨论结论。** 倾向于将标题中的 Memory 改回 Knowledge；具体标题尚未定稿。以论文派生知识与产物作为管理对象，更能约束当前研究范围。

Agent memory 的研究涵盖多个维度：事实、经历、过程与技能是内容类型；形成、检索、整合和遗忘是管理机制；个人、项目与跨主体共享是归属范围。它们不是一套必须全部实现的功能清单。[1]

对 PaperWeave，memory 可以描述这些知识对 Agent 的长期作用，但不应单凭这个词扩充系统。

- Skill 是否进入研究，应由工作负载中的积累与维护需求决定。
- 把 Skill 作为有版本的 Artifact 保存，可以沿用现有机制；从经历中自动提炼、筛选、评价和改进 Skill，则是另一组研究问题。
- 修订、删除与过时提示已经有明确的管理语义。它们不自动要求增加遗忘策略。

**边界。** 本轮没有否定已有“Skill 作为 Artifact 类型”的方案。收回的是“为了配得上 Memory，必须纳入 Skill 和完整记忆生命周期”的理由。Skill 是否作为核心实例、扩展或使用指导，仍应按任务需要确定。

## 2. 投数据库会议，贡献应当怎样组织？

**你的问题。** 面向固定研究意图设计 schema，似乎不足以单独构成有效贡献；多 Agent 在共享库上持续协作的理念、支撑它的机制，以及评测，能否组成三项贡献？

**讨论结论。** 可以按下面三项组织，但每项都需要具体落点：

| 贡献 | 应当落成什么 |
| --- | --- |
| 问题与工作负载 | 刻画不协调写者共享积累的设定、失败模式、写者任务和读者需求，形成可证伪的问题 |
| 管理机制 | 给出身份、来源、修订、解释并存、版本、依赖与访问的管理语义，以及它们怎样由接口执行 |
| 实证发现 | 通过可复现的负载与评测，揭示退化规律、机制作用、适用边界和代价 |

Schema 为这些机制提供表达基础。“为任务定义了一套字段”本身不能充分说明贡献；需要说明这个表达怎样支持所需的管理语义。

评测如果形成可复现的工作负载或新的实证发现，可以构成贡献。仅仅“做了实验”属于验证工作。负结果可以有研究价值，但要解释它揭示了什么边界；它也不自动证明所提机制有效。

**边界。** 多写者积累的理念是否新颖，仍需相关工作核查。本轮认可它作为问题切入点，不视为已经证明的首创性。

## 3. 数据库健康度与下游工作流支持度怎样分开？

**你的问题。** “后来者能否找到并正确使用知识”属于工作流支持度；你还需要单独评价库本身。

**讨论结论。** 保留两个分开的评测对象：

| 评测对象 | 要回答的问题 | 验证依据 |
| --- | --- | --- |
| 库的完整性与维护正确性 | 库状态是否满足规则，写入与变化后是否仍满足；记录、依赖和历史是否可信 | 当前状态、源材料、引用、文档、提交记录及预先规定的变化场景 |
| 下游工作流支持度 | 积累的内容是否足以完成研究任务，Agent 能否定位并正确使用它 | 独立读者执行工作流或探针的结果 |

正确记录被后续写入写坏或丢失，是库状态层面的知识流失；记录仍然正确，但读者找不到或用错，是访问或下游使用层面的问题。前期回答把这些混在一起，后续讨论已将其分开。

“数据库健康度”可以作为工作名称。正式表述可采用“数据完整性与维护正确性”，并明确各指标，避免把它当成一个未定义的总分。

## 4. 从关系数据库出发，哪些性质适合检验？

**你的问题。** 除重复与悬空引用，还有哪些属于数据管理本身、适用于 PaperWeave 的性质？是否需要为投稿补齐事务原子性等评测？

**讨论结论。** 评价你实际提供或改变的管理语义。关系数据库的唯一约束、外键、非空与检查约束，提供了直接参照。[2] 版本、谱系、派生维护则对应你进一步提供的能力。

| 性质 | PaperWeave 中可检验的内容 | 当前讨论中的对应 |
| --- | --- | --- |
| 键与身份完整性 | 同一对象重复、不同对象误合并、同一产物身份键上多份文档 | M1、M2、M4 |
| 参照完整性 | 对象、材料、产物行的引用是否可解析；修改或删除后是否失效 | M3 |
| 契约完整性 | 必要署名与来源是否缺失；关系端点、引用格式、锚点范围是否符合声明规则 | 写入契约与审计 |
| 更新保护 | 旧版本编辑是否覆盖新改动；他人的受保护判断是否被改写；修改理由是否留存 | 版本校验、M7、M10 |
| 历史与版本正确性 | 历史状态是否准确重建；旧引用是否固定到原版本，避免随当前状态漂移 | AsOf、Diff、版本引用，值得补齐 |
| 派生依赖维护 | 按声明规则应受影响的对象是否被提示；漏报和误报有多少 | M9 与依赖检查 |
| 图与文档一致性 | 图中登记的当前文档、哈希和依赖是否与实际文档一致 | 值得补齐 |

另外，M5 应当区分“数值错误”和“来源、对象、条件或版本绑定错误”：数值可以正确、引用可以存在，但它属于另一个实验。M6 检查原先正确且仍应保留的知识是否被写坏或丢失；合理修订和撤回要排除。

**取舍。** 现有 M1–M11 已经覆盖较多状态问题。新增重点是历史重建、引用版本固定、图与文档一致性，不需要无限扩展指标。

评测可分为可控场景与长期时间线：前者检查机制是否按规则执行，后者观察真实写入中的违规率与退化。后端已有且本文没有改造的事务能力，不必成为主要评测对象。

基本约束检验能证明实现按契约工作；要进一步说明共享积累的价值，还需独立核验语义忠实度、知识流失等结果，并报告成本。

## 5. 版本管理能否解决项目文档之间的描述不一致？

**你的问题。** 文件加 Git 能保存修改历史，但一份文档改了，另一份相关文档可能仍保留旧说法。PaperWeave 是否也会出现这种问题？模型是否能处理？

**讨论结论。** 同样可能出现。版本记录、依赖提示和语义一致性是三件不同的事。

仓库中已读到的一个例子是：最新讨论将 ProjectView 改为只读扩展，旧文档仍保留 Fork/Merge。Git 保存了演变过程，文档同步仍需另行完成。

在 PaperWeave 中：

- 引用同一条论文来源化记录，可以减少相同内容的独立副本；修订后共享一个当前值，但记录仍可能抽错。
- Artifact 将记录组织成比较、判断与报告，更容易保留旧说法。若它显式依赖被修订的记录，库可以提示可能过时。
- 未登记的语义依赖，以及粒度过粗的引用，仍可能漏检。例如只引用整篇论文，未关联被修订的具体实验记录。

**模型目前能够支持的表述。** 依据已登记的依赖，暴露可能失配的产物；覆盖程度取决于依赖的完整性与粒度。

评价文件加 Git 时，应在相同论文知识与产物上比较变化影响的遗漏，不能直接把自由项目文档中的全部语义不一致当成系统已经能够解决的负载。

## 6. 是否增加修改证据后的强制依赖检查？

**你的提议。** 一个节点作为证据被其他对象引用，Agent 修改它时，库要求 Agent 检查依赖者是否也需要修改。这样能否避免变化后忘记同步？

**讨论结论。** 值得作为后续会议版本的机制候选。它把变化影响的检查变成可执行的写入义务。

候选流程：

1. Agent 提交证据记录的修改，库返回显式依赖它的对象清单。
2. Agent 逐项给出处理结果：已更新；检查后仍有效；暂无法判断并标记待复核。
3. 库校验清单是否逐项处理，记录结果、理由与相关修改；遗漏处理时阻止提交。

库确定依赖范围、执行契约，Agent 判断语义影响，延续现有职责边界。

**强制检查，不强制所有对象都更新。** 有些结论不受此次变化影响；固定引用旧版本的文档也可能继续有效。解释层的合理分歧同样需要保留。

**保证范围。** 在清单和处理规则成立的前提下，已登记依赖上的变化不会被无声略过。它不能保证语义完全一致：Agent 可能判断错，依赖可能漏记，更新后的对象还可能影响下一层对象。

可测量影响清单的漏报与误报、逐项处理的覆盖程度、语义判断正确率，以及维护开销。

**状态与待定。** 这是本轮的新机制建议，尚未实现，也未冻结为正式契约。直接或传递依赖的范围、“待复核”的提交规则、下一层影响怎样继续处理，需要进一步确定；本轮不将其直接加入 arXiv v1 的必做范围。

## 7. 成本没有明显优势，应当怎样表述？

**你的问题。** 增加数据库管理机制可能更贵。如果在接近的成本下实现接近的任务效果，是否已经可以接受？

**讨论结论。** 成本可以定位为机制的代价是否可接受，不必主张成本领先。草案中的 E3 对应“效果非劣效加成本账本”。

“数据库天然比文件直接使用更低效”不成立：定位、关系导航和影响范围查询可能减少 Agent 的扫描与上下文处理，但这需要实测。

| 比较对象 | 成本口径 |
| --- | --- |
| 文件加 Git | 多付出了多少成本，换来了多少完整性、可追溯性与维护保障 |
| Graphiti 等 memory 系统 | 在预先声明的质量差距内效果非劣，构建和使用成本可接受；内部模型调用全部记账 |

成本分开报告构建、产物写回、变化维护和下游读取。失败调用、被拒后的修复及绕过读取也应计入。

相近成本与相近任务效果可以支持 E3；核心研究价值仍需由共享积累的管理结果支撑。只有后续使用确实更便宜，才能进一步主张构建成本能够摊销；不能预设一定存在盈亏平衡点。

**边界。** 非劣效阈值和可接受成本尚需在正式协议中确定。按当前 arXiv v1 范围，E3 留到会议版本。

## 8. 图数据库上的连接与 Artifact 是否有优化空间？

**你的问题。** Artifact 常由多个节点的内容组合、再经 Agent 计算形成。图数据库是否还存在连接效率问题？

**讨论结论。** 存在。Neo4j 的执行计划有节点与属性值的 Hash Join，图结构不消除连接成本。[3] 你的场景可以分为三层：

| 层次 | 优化空间 |
| --- | --- |
| 后端结构化连接 | 索引、连接与遍历顺序、中间结果规模；主要由 Neo4j 的查询优化器处理 |
| Agent 语义组合 | 先用任务、数据集等结构条件缩小候选，减少可比性、证据支持等昂贵判断 |
| Artifact 复用 | 保存已经组织和判断过的结果，在任务适用、依赖状态允许时复用，减少重读与重复判断 |

Artifact 可以类比为包含 Agent 判断的物化结果；不是每个 Artifact 都严格对应一个关系连接。它还保存条件、依据和综合结论。保存结果与输入可能不同步，是派生内容维护的基本问题；当前策略是提示可能过时。[4]

例如，实验比较先按任务和数据集过滤，再让 Agent 检查训练协议；可复用已有的有效判断，变化后复核受影响部分。

**边界。** 这些是性能收益的候选来源，不是已经证明的优化贡献。测量应区分后端查询时间、候选组合数量、重复读取、语义判断次数和 token 成本，并同时保持质量对照。

## 9. 本轮意见的确认程度

| 类别 | 整理结果 |
| --- | --- |
| 研究定位倾向 | Knowledge 更适合约束当前范围；具体标题未定，Skill 不应由标题倒逼进入核心 |
| 贡献组织 | 问题与工作负载、管理机制、实证发现；新颖性和有效性仍需证据 |
| 评测分工 | 库的完整性与维护正确性，和下游工作流支持度分别评价 |
| 指标取舍 | 现有健康度框架较充分；优先补历史、版本引用和图—文档一致性 |
| 新机制候选 | 修改证据后的强制依赖检查，保留“仍有效”和“待复核”等处理状态 |
| 成本定位 | 可接受的管理代价；对 memory 系统做非劣效与分项成本比较 |
| 性能探索 | 减少候选组合、重复读取和重复语义判断；结果需实测 |

后续需要明确的事项集中在：标题和 Skill 的位置；依赖检查的范围与提交规则；指标的判定口径；质量阈值与成本预算。当前没有修改代码、仓库设计文档或正式评测协议。
